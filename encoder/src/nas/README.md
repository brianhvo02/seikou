# nas/: the encoder and Seikou's NAS

The encoder talks to Seikou's NAS server only through its HTTP API, as a paired owner device, the way Seikou's app does: pairing redeems an owner pairing code with a new P-256 public key, and every run signs the NAS's session challenge with that key for a session token. This folder holds the pairing file, the pairing itself and the client that makes requests with a session.

## Concepts

- **The pairing file.** `<data>/nas.json`, written atomically with mode 0600: the NAS's API base, the device id and person the NAS gave, the person's name, the device's private key as a JWK (generated extractable so it can be kept) and when it was paired. It never holds a session token. A file that cannot be read as one counts as no pairing.
- **The API base.** Always ends in `/api/`. It must be `https:`; plain `http:` is allowed only on `127.0.0.1` and `localhost`, for tests. A user name, password, query or fragment is refused or dropped.
- **Pairing input.** A typed code with the address, or a pairing link as Seikou makes them: `?pair=<code>&nas=<API base>`, or `?pair=<code>&rv=<rendezvous Worker>`, in which case the Worker's `POST codes/lookup { code }` gives the NAS's HTTPS base (`routes.https`). Codes are normalised as `@seikou/nas/pairing-code` does.
- **Owner only.** A code for a person who is not an owner is refused (`not-owner`) and nothing is saved. The NAS has still paired that device, so it shows in Seikou's admin screen until an owner removes it; the same goes for a device whose pairing the encoder forgot (Unpair).
- **Sessions.** The client holds one session token in memory, signs for a new one 60 s before the NAS says it lapses, and shares one sign-in between the requests waiting on it. The sign-in runs under its own 15 s timeout, never a caller's signal: a caller whose signal aborts stops waiting alone (`unreachable`). A sign-in answer that is not JSON, or has no non-empty `token` and numeric `expiresAt`, is `http` with a fixed message. A request answered 401 signs for a new session once and is sent once more; a second 401 is the answer.
- **Closing.** `close()` drops the key and the session; every later request throws `NasError('unauthorized', null, 'This app is no longer paired with the NAS.')`. The backend closes the client it replaces on unpair and re-pair, so a long job holding the old one stops.
- **Mirrors.** A NAS disc the encoder works on becomes `<data>/fetch/<disc key>/`, a folder that reads as an ordinary disc folder: its metadata files whole (inlined ones straight from the manifest), every file under `BDMV/STREAM/` a sparse file of its true size holding only the ranges fetched, and `fetch.json` (`{ discId, discIds, metadataFrom, discKey, label, files: { path: size }, ranges: { streamPath: [start, endExclusive][] }, heads }`, manifest paths, written atomically (temp file, rename, folder flushed) after each chunk is flushed). Folders keep the manifest's upper-case names and file names are lower-cased (`BDMV/PLAYLIST/00000.mpls`, `BDMV/STREAM/00001.m2ts`, `BDMV/index.bdmv`), the names `loadPlaylist`, `probeClip`, `readPmt` and the job runner open, so a mirror reads the same on a case-sensitive filesystem; `discKeyOfFolder` of a mirror is the NAS's own key. A mirror whose stream files (names and sizes) differ from the NAS's manifest is removed, held or not, and the open fails `disc-changed`; one whose streams match keeps what it fetched. Copies of one disc share a key and may differ in metadata: opening another copy rewrites the metadata in place when no holder claims any clip or the mirror itself (`claimMirror`: a helper session claims its mirror as `session:<id>` for the server's life, since it plans from the metadata without holding clips), and leaves it as the running work started with it otherwise. `discId` is the latest copy opened, `discIds` every one and `metadataFrom` the one whose metadata is on disk; a copy whose streams change (re-ripped under the same id) only leaves `discIds` of a mirror other copies still share, and removes a mirror it alone made; a range a 404 refuses under one id is asked for under the others before the disc counts as changed.
- **Fetching.** A `ClipFetcher` fetches clip heads (`HEAD_BYTES`, what probes and PMT reads need) and whole clips for a holder (`job:<id>`, `session:<id>`), in `CHUNK_BYTES` range requests written in place. Holders live in memory, per data directory and disc key, shared by every fetcher of the app; a clip no holder claims is emptied back to its head once any download of it has finished and if no holder has claimed it meanwhile: the shrunken ranges are recorded first, then the file is truncated to the head and back to its size, so the record is never larger than the file, and `sweepUnheld` does that for every mirror when the queue runner starts. Before a fetch the missing bytes plus `ROOM_MARGIN_BYTES` must fit the drive's free space (`statfs`), else `no-room`. Each request is retried after 1, 2, 4 and 8 s on a network error or 5xx, then fails `unreachable`; a 404 or a `Content-Range` total that is not the manifest's size is `disc-changed`. Two holders asking for one clip at once share one download.
- **The NAS's library.** `NasLibrary` (one per app, `nasLibraryOf(app)`) walks the NAS's `GET library?path=` from the top (each disc once by id, however many group folders list it) and fetches each disc's manifest, at most 4 at a time, for its key (`discKeyOf(id, manifest.files)`) and playlist count. `<data>/nas-library.json` keeps the listing with the NAS's API base: a disc whose id and `sizeBytes` match the saved one is not asked for again, and a NAS that cannot be listed keeps the last listing (`reachable: false`), also across runs. A disc whose manifest fails is listed nowhere until a later scan gets it. Its discs are those of the NAS the app is paired with now; a pairing change drops them from memory (`forget`), and a scan asked for while one for an earlier pairing runs starts afresh. The library scan (`src/server/library.ts`) runs it beside the local scan while paired, and pairing starts one.
- **Uploading.** `uploadEpisode` sends an episode's MKV into the NAS's Encodes library through Seikou's resumable upload, named `<anilistId>-<episode>.mkv` (the NAS files it by the MKV's own `ANILIST_ID` and `EPISODE` tags): the file is hashed once (SHA-256, kept in the caller's `UploadState` with the NAS's upload id, the size and the bytes sent, so a job can keep it and resume), `POST encodes/uploads` opens the upload (the NAS answers this device's own open upload of the same file with its id, so an answer lost on the way back is resumed, never locked out; the ranges are then asked for), `GET encodes/uploads/<id>` tells which ranges a stored id already holds (404: the NAS forgot it, so it starts over), the missing ranges go in order as `PUT`s of `UPLOAD_CHUNK_BYTES` (8 MiB, as bytes, so a 401 can send them again), and `POST encodes/uploads/<id>/complete` files the episode and gives its encode id (`entry.id`, or `filed` when the NAS filed it but could not list it yet). Each request has 60 s to answer and is retried after 1, 2, 4 and 8 s on a network error, a 5xx or that timeout, then fails `unreachable`. The NAS's refusals become `UploadError` codes: 409 `in-progress` (another device's open upload of the name) is `refused`, saying it is removed after 24 hours unused; 422 `hash-mismatch` starts over once (hashing again), then is `refused`; 422 `bad-tags` is `bad-tags` (the upload is dropped on the NAS, which keeps such uploads); 507 `no-room` is `no-room` with the NAS's message; 503 `encodes-folder-unavailable` is `folder-unavailable`; 404 `not-configured` is `not-configured`; 403 (`https-only`, not an owner), 429 and anything else are `refused`. A 409 `incomplete` asks which ranges are missing and sends them. The encoder never counts an episode as uploaded before the `complete` answer.
- **Secrets.** Nothing here logs. No error message holds the token, the key or a query string: messages name the NAS by host name only.

## API

- `nas-store.ts`: `NasPairingFile`, `readNasPairing(dataDir)`, `writeNasPairing(dataDir, p)`, `removeNasPairing(dataDir)` (also removes `<data>/fetch` and `<data>/nas-library.json`, which belong to the NAS forgotten).
- `pairing.ts`: `checkNasBase(base)`, `parsePairingInput({ code?, base?, link? })` and `pairWithNas(dataDir, input, deviceName, fetchImpl?)`, which writes the new pairing first (renamed over any earlier `nas.json`), then, when it replaced one, removes what was fetched (`removeNasFetched`), and resolves with the new file. `removeNasFetched(dataDir)` is in `nas-store.ts`.
- `client.ts`: `NasError { code, status, error }` with `code` one of `unreachable` (no answer, abort or timeout), `unauthorized` (the NAS no longer knows the device, or refused its session), `not-owner`, `bad-address` and `http` (another error answer: `status` and the body's `error`; a malformed code is `http` 400 too). `NasClient.load(dataDir, fetchImpl?)` is null when not paired; `base`, `personName`, `request(path, init?)` (a path under the base, such as `encodes/status`; pass a body that can be sent twice), `json<T>(path, init?)` (an error answer throws, 401 as `unauthorized`), `me(init?)`, `close()`.
- `nas-library.ts`: `NasDisc { discId, key, label, relPath, playlistCount, sizeBytes }`, `NasLibrary` (`scan()`, never rejecting; `scanning`; `reachable`, null before the first scan; `discs()`; `byKey(key)`; `forget()`) and `nasLibraryOf(app)`.
- `mirror.ts`: `HEAD_BYTES`, `CHUNK_BYTES`, `ROOM_MARGIN_BYTES`, `FetchError { code: 'disc-changed' | 'no-room' | 'unreachable' }`, `ensureMirror(dataDir, client, discId, expectedKey?)` (resolves `{ dir, key, label }`), `mirrorDirOf(dataDir, key)`, `isMirror(dir)`, and the shared pieces (the holder registry and lock, `fetch.json`, range requests with the retries, `localPathOf`).
- `fetch.ts`: `ClipFetcher({ dataDir, client, key, signal?, onProgress?, sleep?, freeBytes? })` with `heads(playlistId)`, `hold(holder, clips)` and `release(holder, clips?)` (clips as `00001.M2TS`); `releaseHolder(dataDir, key, holder, clips?)`, the same release without a client (the job runner lets go of a job's clips with it, paired or not); `claimMirror(dataDir, key, holder)` and `releaseMirror(dataDir, key, holder)` (a claim on the mirror's metadata); `sweepUnheld(dataDir)`; `clipsOfEpisode(discDir, playlistId, episodeSpec, index)` (1-based, the clips of the plan's segments, through `episodeItems`, needing no clip bytes); `readMirrorRange(dataDir, client, key, path, start, end, signal?)` (inclusive; fetched bytes from the mirror, the rest from the NAS, never stored; an abort of `signal` stops the NAS requests and their retries); `assertFetched(dir, clips)` throws `Clip <name> is not fetched from the NAS yet` for the first clip a mirror does not hold whole (by its `fetch.json`; a folder that is not a mirror passes), and `assertPlanFetched(plan)` does it for a plan's segment clips: a guard run before anything reads clips past their heads (`encodePlan` and `encodeEpisodes` before BestSource and the PG reader, the line-up's decode).

## Where to look

- The backend holds the client in `AppContext.nas.client` (`src/server/http.ts`), loaded at `app` and `serve` start and replaced by `src/server/nas-routes.ts` (`GET /api/nas`, `POST /api/nas/pair`, `DELETE /api/nas`).
- Seikou's side: `server/src/routes/pair.ts` (redeem, challenge, session), `server/src/auth.ts` and `scripts/verify-level.ts`, whose `Device` this client follows.
- `upload.ts`: `UPLOAD_CHUNK_BYTES`, `UploadState { id, sha256, size, sent }`, `UploadError { code }` (`unreachable`, `no-room`, `bad-tags`, `folder-unavailable`, `not-configured`, `refused`), `uploadEpisode(client, path, name, state, { signal?, onProgress?, onState?, sleep?, chunkBytes? })` (resolves with the encode id; changes `state` in place and tells `onState`) and `abandonUpload(client, id)` (a best-effort `DELETE` of an upload no job resumes).
- Tests: `encoder/tests/nas/` (`upload.test.ts` uploads copies of `fixtures/encodes/990001/1.mkv` retagged by `retag.ts` as made-up AniList 990002; `mirror.test.ts` and `fetch.test.ts` mirror disc1 of the stand-in, whose clip 2 `fetch.test.ts` lengthens past 16 MiB, since APFS fills the holes of smaller files), against Seikou's NAS handlers run in-process by `nas-test-server.ts` (`startNasTestServer({ encodes?, discs?, prepare? })`, `prepare` changing the library copy before its scan: a copy of `fixtures/synthetic` as library root `syn`, an encodes folder holding episode 1 of AniList 990001 with uploads, codes minted through its `Auth`, `expireSessions()`, which moves its clock past every session it gave, and `pause()` and `resume()`, which close its port and open it again with its state kept, for a NAS that stops answering).
