# server/: the app's local backend

The encoder app (`seikou-encode app`) and its subtitle helper are one web page that runs on the user's own machine. This backend serves that page and its API from one origin on `127.0.0.1`: the disc library, the discs the page plays (in `@seikou/engine`, read over HTTP exactly as Seikou reads a NAS disc), playlists and chapters, settings profiles, the encode queue and its runner, and the helper's routes (the episode plan, titles, fansubs, alignment, the saved record). It holds helper sessions: each is the helper working on one disc, one playlist and one episode list, fixed when the session is made, under an id of its own; the page of session `<id>` is `/helper/<id>`, and its routes are under `/api/sessions/<id>`. `seikou-encode serve` starts the backend, makes one session and opens its page.

## Concepts

- **App context.** `AppContext` holds what the backend keeps for its whole life: the data directory, the run's token, the page's folder, the external tools (or null when they are missing), the outside sources (SeaDex, Anime Tosho, AniList and its cover images) and the library folders (`roots`; `serve` gives none), and the NAS holder (`nas.client`, the `NasClient` of `src/nas/` while the encoder is paired, else null; loaded at start and replaced when the page pairs or unpairs). Tests pass recorded sources. Caches every session shares (the release cache, the cover URLs AniList gave, the discs read) are kept per app context.
- **Helper sessions.** `HelperSession` is `{ id, discDir, discKey, playlistId, episodeSpec }`; `SessionStore` (`sessions.ts`, one per app, `sessionsOf(app)`, also `server.sessions`) makes them on demand and keeps them, in memory, for the server's life. Making a session for the same disc folder, playlist and episodes again gives the same session; episode lists that cut the playlist alike (`1-3,4-` and `1-3,4-5` on five chapters, `1-3, 4-5`) count as the same (`sameEpisodeList` in `plan/episodes.ts`, which the record routes and the encode's record check use too), so a saved record loads for any spelling of its list. A session's episode plan is kept per session; the decoded episode audio is one cache per app keyed by session and episode, so its budget does not grow with sessions. Two pages on two sessions work side by side.
- **Disc key.** The disc is named by `discKeyOf(id16, manifest.files)` from `@seikou/nas/disc-key`, where `id16` is the first 16 hex digits of the SHA-256 of the disc folder's real path. A disc with streams gets its content fingerprint (`f.<hex>`), so the same disc keeps its key in another folder; the key names the saved record.
- **The NAS disc API.** The manifest (every file under BDMV and CERTIFICATE, upper-case, with the small metadata files inlined) and range reads are answered by Seikou's own NAS modules (`server/src/manifest.ts` and `server/src/ranges.ts`), so the engine's `RemoteSource` and `HttpTransport` open the disc unchanged. File paths are matched in any case.
- **Playlist time.** Episode times are microseconds from the playlist's start. An episode starts at its first frame (its first chapter's mark rounded to the nearest frame, `firstFramePlaylistUs`), the zero of the encode, the alignment and the retimed track; its length is its whole frames at the video's rate, as the encoder will cut it (the planner, `planEpisodes`, reads the start of each clip the session's episodes play once per session for its first timestamps and its PMT, and cuts the playlist's first STN audio stream).

## Security model

The server listens on `127.0.0.1` only, so nothing else on the network can reach it. Any web page the user has open can still send requests to it, so:

- **A token per run.** Each run gets a fresh random token (`app.token`, made by whoever starts the server); every `/api/` request must carry it as `Authorization: Bearer <token>` or `?t=<token>` (the engine's file reads use the query, so they need no preflight). Without it: 401 `unauthorized`. Tokens are compared in constant time.
- **The Host header.** Every request, page or API, must name `127.0.0.1:<port>` or `localhost:<port>`; anything else answers 403 `bad-host`. This stops DNS rebinding, where a page re-points its own host name at 127.0.0.1 to read the answers as same-origin.
- **Paths.** A path with an empty, `.` or `..` segment (also percent-encoded), or one that decodes to a slash, backslash or NUL, answers 400 `bad-path`. Disc files are found by listing each directory under BDMV or CERTIFICATE, never by joining the request's path, and page files must resolve inside the page's folder. The page's own routes (`/helper/<id>` and the like) are answered with its index.html, after the same Host and path checks.
- **Covers.** The page is cross-origin isolated, and AniList's image host sends no `Cross-Origin-Resource-Policy`, so the page cannot show its images; the backend passes each cover on from its own origin (`covers.ts`), fetching only URLs AniList gave it in this run's lookups (searches in any session, and the app's searches and entries), kept per run by AniList id.
- **No CORS.** No answer carries `Access-Control-Allow-Origin`, so another origin cannot read the API even with the token.
- **Isolation.** Every answer carries `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Embedder-Policy: require-corp` and `Cross-Origin-Resource-Policy: same-origin` (the engine needs `SharedArrayBuffer`); API answers carry `Cache-Control: no-store`.

## API

- `startHelperServer(app, port = 0)` listens on `127.0.0.1:<port>` with no session and resolves to `{ url, port, sessions, close() }`; it rejects when the port cannot be bound.
- `sessions.ts`: `SessionStore` (`create({ discDir, playlistId, episodeSpec })`, which reads the disc and checks the playlist and episode list and rejects with `SessionError { status, code }` (400 `bad-request` for a playlist id that is not five digits, 404 `not-found` for a missing playlist, 400 `bad-episode-spec`) or with the read error for a folder that is not a disc; `get(id)`; `byDiscKey(key)`, the folder of a disc a session is on or the last scan found, and `discDirOf(key)`, the same but a key nobody knows yet waits (60 s at most) for a running library scan to end, then is looked up as a NAS disc (`mirrorDirFor(key)`: the disc of the NAS listing with that key made or refreshed as a mirror through `ensureMirror` once per run; while the NAS cannot be reached, a mirror already here is used as it is; null when there is none), which the disc routes, `POST /api/sessions` and a job's retry use; a session made on a mirror first fetches the heads of the playlist's clips (`ClipFetcher.heads`) and claims the mirror's metadata for the server's life; two copies of one disc share a key and so one entry), `sessionsOf(app)`, `discOf(app, dir)` (a disc's key, label and manifest, read once per app) and `sessionStoreRoutes`.
- `http.ts`: `AppContext`, `HelperSession`, `HelperSources`, `Route` (`(req, res, match, app, session) => Promise<void>`, with `match` the route's pattern run on the still percent-encoded path, and `session` null for an app route), `SessionRoute` and `sessionRoute(route)` (a route that always has a session), `RouteTable` (`[method, pattern, route]` entries), `json(res, status, body)`, `httpError(res, status, code, message?)` and `sendFile(req, res, path, size, headers)` (whole or one range).
- A route module exports its `RouteTable`s; `server.ts` concatenates them in `APP_ROUTES`, matched on the whole path, and `SESSION_ROUTES`, matched on what follows `/api/sessions/<id>` (empty for the session itself). An id no session has answers 404 `no-session`, a path that matches with another method 405 `method-not-allowed`, no match 404 `not-found`, a route that throws 500 `internal`. Errors are JSON `{ error, message? }`.

Episodes are numbered from 1 in the session's episode list, and their times are milliseconds from the episode's first frame. Lining up decodes the episode's audio through vspipe once (BestSource keeps its index under `<data>/bestsource`, where the encode finds it too) and keeps the last two decodes, of any session, in one cache per app; decodes run one at a time, and a client that goes away stops a decode no other request waits for. Track ids repeat between a release's files, so the subtitle route names the file as well as the track.

There is no automatic lookup of the show from the disc: the AniList id is whatever the user searched for and picked. A failing or throttled upstream answers 503 `source-unavailable` with the failing `source` (`anilist`, `seadex` or `tosho`); an Anime Tosho release that does not exist answers 404 `not-on-tosho`. Uploads wait in `<data>/uploads/<batch>/` until commit.

A `<discKey>` of no disc a session is on or the library holds answers 404 `disc-changed`, which the engine reports as a changed disc. An `<id>` no session has answers 404 `no-session`.

## Where to look

- `server.ts`: the listener, the Host, path and token checks, routing (app and session tables) and the page's files.
- `http.ts`: the app context, session and route types and the answer helpers.
- `sessions.ts`: the helper sessions, the discs they are on, and `POST /api/sessions`.
- `library.ts`: the disc library (`scanLibrary`, and `Library` per app, `libraryOf(app)`: the last complete scan of the saved and run roots, one scan at a time; `idle(timeoutMs)` waits for the running one). `library-routes.ts`: its routes, the playlists and chapters of a disc and the roots setting (`subs/app-settings.ts` keeps `settings.json`).
- `profiles.ts` and `profile-routes.ts`: settings profiles (`EncodeSettings`, `ProfileStore` over `<data>/profiles.json`, `profilesOf(app)`, `parseSettings`). Settings carry `destination`, `folder` or `nas` (settings saved before it read as `folder`). The built-in `default` profile (CRF 25, preset 4, film grain 4, no extra SVT arguments, Opus default, PGS on, no web package, `episode-{n}`, a folder) is not in the file and cannot be changed or deleted (400 `built-in`). Names are unique in any letter case. A bad value answers 400 `bad-setting` with `field`; extra SVT arguments the encoder sets itself (`--crf`, `--preset`, `--film-grain`, `-i`, `-b`, `--output` and the like, also as `--name=value`) are refused. A missing file is only the default; a damaged one leaves only the default (logged once) and refuses writes with 500 `profiles-unreadable`, so it is never overwritten.
- `jobs-lock.ts`: one queue per data directory. `takeJobsLock(dataDir)` creates `<data>/jobs.lock` with O_EXCL holding the pid and answers `{ lock }`, or `{ heldBy }` while a live process (this one included) holds it; a lock whose pid is gone (`process.kill(pid, 0)` fails with ESRCH) or that holds no pid is stale and taken over. `JobsLock.release()` removes the file unless another process took it over, and every lock still held is released when the process exits. `app` takes it before starting and refuses to start (exit 1, one line naming the pid and the data folder) when it is held; `serve` lets its runner try, and a runner that cannot take it runs nothing (`queueElsewhere` is the holder's pid; every queue route answers 409 `queue-elsewhere`).
- `jobs.ts` and `job-routes.ts`: the encode queue (`JobRunner`, one per app: `startJobRunner(app, deps?, lock?)` makes and starts it, taking the queue lock unless given one, `jobRunnerOf(app)` finds it; `JobStore` over `<data>/jobs.json`; `jobCli`; `namesCollide`, `defaultOutDir`, `isJobFile`; `waitingFor()` says what a stop waits for, `the tool chain` or `packaging episode <n>`, for the line the first Ctrl-C prints). A job may carry `only` (1-based episodes of its `episodeSpec`, non-empty and distinct, else 400 `bad-request`; all of them is the same as none): the other episodes are created `done` with `skipped: true` (shown as "Already encoded", left out of progress and ETA), never fetched, encoded or uploaded, and left out of the NAS checks and of `output-in-use` (names come from the episode's number, so disjoint episodes of one list never meet); the subtitle record is still checked and loaded against the whole `episodeSpec`, so episode N keeps its own retimed subtitles, and `only` is kept in `jobs.json` (its `cli` ends with `--only <list>`). Jobs run one at a time in order; a queued test job runs first, at the running encode's next episode boundary, and the encode then resumes ahead of the others (`paused`). The runner calls `encodeEpisodes` once per episode it still needs (`onlyEpisodes`), with the job's copy of the settings (`pgs: false` is `noPgs`, `web: true` is `webDir: <outDir>/web`), the BestSource cache in `<data>/bestsource`, the record read once per run and an `AbortSignal` for cancel. An episode is done once the runner sees its closing 100% `progress` event or `episode-done` (with the web package, `packaged`); a file found on disk never counts, but one whose rename the closing event reported does, even when an abort lands before `episode-done`. Retry encodes only the episodes not done and packages again (`packageEpisode`, no encode) those whose packaging failed, unless the record's `savedAt` differs from the job's `recordSavedAt`, when every episode is encoded again (an upload the NAS still holds for one is dropped there). A job on a NAS disc (its folder a mirror) fetches each episode's clips before encoding it (`ClipFetcher.hold('job:<id>', …)`, the `fetching` step), starts fetching the next episode's clips while it encodes (that fetch's failure is reported by the next episode's own fetch step, which waits for it), and after the MKV is complete lets go of the clips no later episode needs; a job that ends (done, failed, cancelled, interrupted) lets go of every clip it holds, while one paused for a test keeps them. A fetch that finds the disc changed on the NAS (`disc-changed`) fails the job with `The disc <label> changed on the NAS since it was opened. Open it again from the Library and queue it again.` (`discChangedMessage`), since a retry would meet the same change. A job whose `settings.destination` is `nas` uploads each episode once its MKV is complete (`uploadEpisode`, the `uploading` step, its `UploadState` kept on the episode and saved as it changes), deletes the MKV once the NAS's `complete` answer gives the encode id, and marks it done; a failed upload marks the episode `upload-failed`, keeps the MKV and fails the job, and an episode that was uploading, or whose upload waited, when the job stopped becomes `upload-failed` too, so a retry resumes the upload. An upload that finds the NAS away (`unreachable`, or its encodes folder missing) does not hold the runner: the episode becomes `upload-waiting` (MKV and `UploadState` kept) and the job goes on with its next episode, whose fetch on a NAS disc passes without the NAS when its clips are already whole and waits otherwise; after each encoded episode the pending uploads (`upload-waiting`, and on a retry `upload-failed`) are tried again in episode order, stopping at the first that finds the NAS away, and once no episode is left to encode the job uploads them, waiting for the NAS as below. A done NAS job's `<data>/nas-out/<id>` is removed, and so is a removed one's, whose uploads left open on the NAS are dropped there too (best effort). A NAS that does not answer (a fetch, or an upload once nothing is left to encode, `unreachable`) or whose encodes folder is missing sets `waiting` and the step is tried again every `nasRetryMs` (60 s) until it goes through, a cancel stopping the wait at once; an app no longer paired, or a NAS that no longer knows it, fails the job with `This app is no longer paired with the NAS; pair again and retry.`, each step taking `app.nas.client` afresh, so a retry after pairing again uses the new one. `start` empties every unheld clip of every mirror (`sweepUnheld`) before the first job. The job's `cli` names a NAS disc `nas:<key>` and the NAS destination `--nas` (no `--out`). At start, running jobs become `interrupted` and the `<name>.mkv.partial` of each of their episodes in their own folder is removed; `shutdown()` does the same for the job running when the process is asked to stop. A damaged `jobs.json` is logged and never overwritten: every job route, the list and the event stream included, answers 500 `jobs-unreadable` until it is fixed or removed. While the runner stops (`shutdown()`), any failure of the running job counts as an interruption, since Ctrl-C reaches the tools too. Logs: `<data>/jobs/<id>.log`, one line per log event and state change. Test jobs write only to `<data>/tests/<id>` and run through the `runTest` dependency (`TestRunner`: the job, an `AbortSignal` and the encode's event callback, resolving with the outcome the runner stores in `job.test`; default `runTestEncode`). A test always runs from scratch: its folder is emptied and its units reset first, so a retry runs it again whole; at start the folder of every interrupted test is removed (one a Ctrl-C saved as interrupted too), and removing a test job deletes it. Tests replace `encode`, `packageEpisode`, `runTest`, the clock, `nasRetryMs`, `nasSleep` (the waits between one NAS request's own retries) and `uploadChunkBytes`; `tests/server/jobs-nas.test.ts` runs NAS jobs against the in-process NAS stand-in.
- `test-encode.ts`: test encodes. `planTest(playlist, episodeSpec)` takes `testStretches` of the first episode (five, evenly spread with the first and last 5% left out, each 10 s or a sixth of the episode when shorter, never overlapping) and each episode's length; `parseTestProfiles` checks the one to three profiles. `runTestEncode(job, { dataDir, tools }, signal, onEvent, deps?)` plans the stretches with `planRanges` and encodes each once per profile with `encodePlan` (the first profile's encode also carries the playlist's first audio stream, at the first profile's Opus bitrate, which every profile's sample shares), packages `<profileId>/<n>.webm` (AV1 and the shared Opus track, `writeWebm` with `audioFrom`; `.partial` then renamed) with the intermediate MKVs in `work/`, removed at the end, and reports each sample encode as one progress unit. It measures `videoBytesPerSecond` per profile from the encoded blocks, and each profile's `audioBytesPerSecond` as the shared sample's scaled by that profile's effective Opus bitrate over the first profile's (`effectiveOpusBitrate`: the set bitrate, else the encoder's 160 kb/s up to stereo and 320 above, by the stream's channels), and counts the audio streams an encode would write (the saved record's for episode 1, else every stream). `projectedBytes(episodeSeconds, result, audioStreams)` is `(video + audio × streams) × seconds`.
- `disc-routes.ts`: the NAS disc API, and a session's info, playlists and episode times.
- `title-routes.ts`: the AniList search, episode titles and covers of a session (`answerSearch`, `answerEpisodes` and `answerCover`, which `anilist-routes.ts` shares, and `toHit`).
- `nas-routes.ts`: the NAS pairing's status, pairing and unpairing (`nasStatus`, `encoderDeviceName`). Pairing and unpairing run one after the other per app, so the holder has a client exactly while `nas.json` exists, and the client they replace is closed. No answer carries the device key or a session token.
- `nas-title-routes.ts`: the NAS's shows and posters (`nasTitlesOf(app)`).
- `anilist-routes.ts`: the same lookups at app level, and an entry with its next season (`pickSequel`).
- `covers.ts`: fetching a cover (`createCoverSource`: https only, a size cap, a timeout, image types only).
- `fansub-routes.ts`: SeaDex, Anime Tosho, uploads and cached releases (one `ReleaseCache` per app, `releaseCacheOf`).
- `align-routes.ts`: lining an episode up against the disc's audio, and the retimed track. The episode plan comes from `episodePlans` in `disc-routes.ts`, the same one a session's `episodes` route answers from. On a NAS disc's mirror the route holds the episode's clips (`clipsOfEpisode`) for `session:<id>`, the holder of the session's mirror claim, through `ClipFetcher.hold`, for the session's last two lined-up episodes only (`KEEP_EPISODES`, as many as the decoded-audio cache keeps): lining up a third lets go (`releaseHolder`) of the oldest one's clips that the two kept do not play, while the mirror claim stays, keeping the fetch's progress for the `fetch` route; the decode checks them with `assertPlanFetched` first. `fetchFailure` (in `sessions.ts`) turns a failed fetch into the status and code it answers.
- `record-routes.ts`: reading and saving the subtitle record (`RecordStore` in `subs/record.ts` does the files), and moving an older record's chapter names into the episode info.
- `episode-info-routes.ts`: a playlist's chapter names and AniList choices (`EpisodeInfoStore` in `plan/episode-info.ts` does the file), for the Episodes page and the helper's Details sheet alike.
- Tests: `encoder/tests/server/`.
