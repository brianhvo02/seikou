# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

青光 (Seikou, "blue light", a pun on Blu-ray; the repo was `bluray-web` before 2026-10-27) is a client-side Blu-ray (BDMV) player for desktop and mobile browsers (Safari, Chrome, Firefox; touch, installable and offline): a TypeScript port of libbluray (not WASM), its own M2TS demuxer, and WebCodecs decoding. Nothing is uploaded. The design spec is `docs/superpowers/specs/2026-10-12-bluray-web-player-design.md`. Milestones 1–4 are done: parsers, demux, H.264/HEVC video, clock, seek/chapters, basic UI, audio (LPCM, AC-3/E-AC-3, the AC-3 core of TrueHD, the DTS core of DTS/DTS-HD, with track switching), HDMV menus (VM, IG menus, UO masks, keyboard/mouse/remote input, menu sounds; spec `docs/superpowers/specs/2026-10-14-m3-hdmv-menus-design.md`), subtitles: disc PGS with forced captions and user SRT files (spec `docs/superpowers/specs/2026-10-15-m4a-pgs-srt-design.md`), and the native ASS renderer with fonts and episode subtitle sets (M4b, spec `docs/superpowers/specs/2026-10-15-m4b-ass-renderer-design.md`). Video shaders (mpv user shaders such as Anime4K on WebGL2) are also in: spec `docs/superpowers/specs/2026-10-15-video-shaders-design.md`. Milestone 5b, the BD-J JVM core, is done (spec `docs/superpowers/specs/2026-10-15-m5b-bdj-jvm-core-design.md`): it boots libbluray's Java stack in a TypeScript JVM. 5c is done too (spec `docs/superpowers/specs/2026-10-16-m5c-bdj-playback-design.md`): BD-J titles drive playback, and BD-J discs no longer open to the title picker. 5d is done as well (spec `docs/superpowers/specs/2026-10-17-m5d-bdj-menus-design.md`): BD-J menus are drawn over the video as libbluray draws them, take keys, mouse and touch, and render their text with FreeType, on desktop browsers and on iPhone and iPad (device gate passed 2026-10-18). 5e is done too (spec `docs/superpowers/specs/2026-10-18-m5e-bdj-library-coverage-design.md`; device check on a real iPhone passed 2026-10-22): every BD-J disc in the NAS library reaches and uses its menu as libbluray does, or fails in libbluray too (the library check, `tools/bdj-library`), discs with MPEG-2 or VC-1 video play without a picture, with a notice, and what a disc saves lasts between viewings, per person on the NAS. Cross-browser and mobile support (step 1 of `docs/superpowers/specs/2026-10-16-cross-browser-and-remote-design.md`, §3) is in too. Step 2 of that spec (§4) is in as well: the NAS disc server behind the user's Caddy at `/bluray`, pairing by code or QR through a rendezvous Worker, ISO discs read through a UDF reader (spec `docs/superpowers/specs/2026-10-17-nas-server-design.md`), and the NAS title library, which browses the NAS by title (spec `docs/superpowers/specs/2026-10-17-nas-library-titles-design.md`). Step 3 (spec `docs/superpowers/specs/2026-10-18-webrtc-people-design.md`) is in as well: people and invites, the NAS store for BD-J saved data, and the WebRTC route that lets a friend abroad play from the NAS with nothing installed (deployed; an iPhone on mobile data paired and played over WebRTC on 2026-10-19, results in the spec's status line). Step 4 phase 1 (spec `docs/superpowers/specs/2026-10-19-lower-quality-design.md`) is in too: the NAS re-encodes a disc on its GPU at lower quality levels and serves each as another version of the disc; phase 2 is in too: the pre-flight picks a level and the player's Quality menu switches it. Fansubs (spec `docs/superpowers/specs/2026-10-23-fansubs-design.md`) are in too: the NAS finds SeaDex-ranked fansub tracks on Anime Tosho, lines them up with the owner's discs and attaches them, and viewers can search Anime Tosho from the player. Resume (piece 2 of `docs/superpowers/specs/2026-10-20-permalinks-resume-design.md`) is in too: a disc remembers where you stopped, with Resume or Start from beginning on opening it, Continue watching and Up next on the NAS title library, and progress on episodes. The subtitle store (piece 3 of the same spec) is in as well: owners upload SRT and ASS files with their fonts to the NAS, attach them to episodes and chapters, and everyone paired picks them from the player's Subtitles menu. The Encodes library (spec `docs/superpowers/specs/2026-11-08-encodes-library-design.md`) is in too: the NAS keeps episodes the Seikou encoder made (AV1, Opus, ASS and PGS in MKV), groups them by show (AniList, TMDB series and films, or the owner's own titles) in an Encodes tab beside Discs, and the player plays them with chapters, Skip opening and ending, and Next episode. `docs/known-issues.md` lists decisions left open on purpose and resolved items, and `docs/roadmap.md` what comes next. Read it before changing something it covers. The player documentation lives in `docs/` (`getting-started.md`, `playing-discs.md`, `nas.md`, `troubleshooting.md`, `self-hosting.md`, `contributing.md`); the site serves the player pages (all but `contributing.md`, which stays on GitHub) under `/help` (`src/ui/help/`: `HelpScreen`, `HelpLink`, `HelpLoadBoundary` for a failed lazy load, `HELP_PAGES` and `helpPath`; `vite/markdown.ts` builds `virtual:help-pages` from `docs/*.md` at build time and rewrites links with `helpHref`; help navigation goes through `NasHistory.pushPath`), so change a page's statements when the behaviour they describe changes.

## Commands

- `npm run dev`: Vite dev server, served with COOP/COEP headers.
- `npm run typecheck` (`tsc -b`) and `npm run build` (typecheck, then `vite build`).
- `npm test`: Vitest, all unit tests (`src/**/*.test.ts` plus `tests/local/**`). Run one file with `npx vitest run packages/bdmv/src/demux/ts-packet.test.ts` and filter by name with `-t "<name>"`.
- `npm run test:e2e`: Playwright against a production build on port 4173 (`npm run build && npm run preview`). Locally Playwright reuses a preview server already running on :4173 (`reuseExistingServer`), so stop a stale one after changing source. `E2E_PORT=<port>` moves the preview server off 4173 when another checkout's preview uses it (`tests/e2e/nas-server.ts` then presents that origin to the NAS stand-in, which still listens on 4191/4192). Those two ports and UDP 47990 (the NAS stand-in's WebRTC route) are fixed and shared across checkouts: run one checkout's NAS E2E at a time. The `chromium` and `mobile-chromium` projects need installed Google Chrome (`channel: 'chrome'`) and a working audio output, because the A/V sync tests measure the real AudioWorklet clock. Run one test with `npx playwright test playback -g "<title>"`.
  - Pick a disc folder with `setFolder` (`tests/e2e/support.ts`), never `setInputFiles(folder)` or `FileChooser.setFiles(folder)`: in Playwright 1.64 those can miss the input's event in Firefox and hang until the test times out.
  - Projects: `chromium`, `firefox`, `webkit` and `mobile-chromium` (the last runs `tests/e2e/mobile-*.spec.ts` and the BD-J menu spec `bdj-menu.spec.ts`, which runs on every project). Run one with `npx playwright test --project=webkit`. Chrome-only specs skip elsewhere with a reason, and `skipWithoutH264` (`tests/e2e/support.ts`) skips H.264 playback where the browser can't decode it, and skips tests that need real-time playback in WebKit on Linux (CI), where it can't keep up; they still run in WebKit on macOS, and real Safari is covered by the device test. CI runs each project on its own runner. Install the others with `npx playwright install firefox webkit`.
  - `SYNC_TOLERANCE_SCALE=2` widens the 20 ms mean / 50 ms max A/V offset bounds. CI uses 1.5. Keep local runs at the default.
  - `ASS_BUDGET_SCALE=8` widens the share of animated ASS draws allowed over the renderer's 8 ms budget from 5% to 40% (`ass-subtitles.spec.ts`). CI uses 8 because its runners miss the budget on 26–29% of draws. Keep local runs at the default.
  - `npx playwright test shaders.spec` runs the shader E2E tests; `SHADERS_GPU=1` adds the Anime4K and A/V sync ones (WebGL2 with float targets; they skip with a reason when it is missing).
  - `LOCAL_DISCS=1 npx playwright test local-discs` plays every disc under `fixtures/local/` and seeks around in it. It also checks the BD-J discs there, including a 5 s warm start-up check on A_NEW_ERA. `LOCAL_DISCS=1 npx playwright test local-bdj-menus` times key presses on A_NEW_ERA's and RENTAL_FAMILY's menus against the 0.2 s bar.
  - Nightly drift test: `npx tsx scripts/make-fixture-disc.ts fixtures/local/long-disc --seconds-per-clip 300`, then `NIGHTLY=1 npx playwright test -g "ten minutes"`.
- `npm run fixture:synthetic`: regenerates the committed discs in `fixtures/synthetic/` from `scripts/` (the scripts build on `tests/helpers/`). Rerun it after changing the builders or muxer, and commit the output. It needs `ffmpeg` with libx264 on PATH for the video fixtures (disc1, disc-menu, disc-subs, disc-bdj, disc-bdj-mixed, disc-bdj-background, disc-speech (`scripts/make-speech-disc.ts`); disc-mpeg2-menu uses its mpeg2video encoder) and the audio fixtures (disc3), and Docker for `disc1.iso` (`scripts/make-iso-fixture.sh`).
- `npm run wasm:build`: rebuilds both WASM modules in Docker (pinned emsdk): `packages/engine/wasm/audio/audio.wasm` and `src/wasm/freetype/freetype.wasm` (FreeType 2.13.2 with Ubuntu's patches, the build libbluray's BD-J harness links). `wasm:build:audio` and `wasm:build:freetype` build one. CI (`.github/workflows/wasm.yml`) rebuilds each and fails on any diff.
- `npm run vm-trace:build` / `vm-trace:golden` / `vm-trace -- <disc> <script> [--dump-pages]`: the libbluray trace harness (`tools/vm-trace/`, Docker; `<disc>` may be a path such as `fixtures/local/<name>`, `<script>` a `.keys` path). `tests/vm-trace/` compares our HDMV VM and Navigator against golden traces from patched libbluray; `vm-trace:golden` regenerates the golden files (never edit them by hand) and CI fails on any diff (`.github/workflows/vm-trace.yml`).
- `npm run test:ass`: Playwright (`playwright.ass.config.ts`, Vite dev server on port 5174) compares our ASS renderer's layout trace and pixels with the committed libass goldens for every `fixtures/ass/<name>/`. `npm run ass-trace:build` / `ass-trace:golden` / `ass-trace -- <file.ass> <fonts dir> <times file>`: the libass trace harness (`tools/ass-trace/`, Docker, libass 0.17.5); `ass-trace:golden` regenerates `tests/ass-trace/golden/` (never edit by hand; CI fails on any diff, `.github/workflows/ass-trace.yml`). `ASS_LOCAL=1 npx playwright test -c playwright.ass.config.ts local` runs the developer's real scripts in `fixtures/local/ass/<name>/` against libass live (see `tools/ass-trace/README.md`).
- `npm run bdj-trace:build` / `bdj-trace:golden` / `bdj-trace -- <disc> [--until <call>[#n]] [--keys <script>]`: the libbluray BD-J trace harness (`tools/bdj-trace/`, Docker). `tests/bdj/` compares our JVM's control-call traces with the golden ones, and `tests/bdj/replay-player.ts` replays a trace or a key script (`tests/bdj/scripts/*.keys`) through the real `Player`; key-script goldens hold control calls and settled plane hashes (`tools/bdj-trace/settled.py`). `bdj-trace:golden` also writes `tests/bdj/golden/local/` from the local BD-J discs when they are present (kept otherwise), which `tests/local/bdj-menus.test.ts` checks without Docker; `bdj-trace:golden` regenerates them (never edit by hand; CI fails on any diff, `.github/workflows/bdj-trace.yml`). `npm run bdj-trace:freetype-golden` regenerates `tests/bdj/fonts/freetype-golden.json` (glyphs and metrics of the bundled font from the harness image's FreeType; `freetype.test.ts` compares `freetype.wasm` with it) and `npm run bdj-trace:text-golden` regenerates `tests/bdj/fonts/text-golden.json` (what libbluray's compiled BD-J font and text natives return and draw; `natives/fonts.test.ts`); both need the harness image, and no CI job regenerates them. `npm run bdj-classlib:build` / `bdj-classlib:collect`: build and collect the class library in `src/bdj-classlib/` (`tools/bdj-classlib/`, Docker; CI `bdj-classlib.yml` rebuilds it and diffs). The harness runs with no network (`--network none`) unless `run.sh --online` is given by hand, which nothing in the repo does.
- `npm run bdj-library:sync` / `bdj-library:check`: the BD-J library check (`tools/bdj-library/`, README there; spec 5e §5). `sync` finds the BD-J discs on the NAS over ssh (`--host` or `$BDJ_LIBRARY_HOST`, no default), read-only and under `ionice`, and copies each disc's start-up files (no clips; a stub `.m2ts` per clip) into `$BDJ_LIBRARY_DIR` (default `~/.cache/bluray-web/bdj-library`, outside the repo, because disc names are private); `sync --video` copies the real clips of a disc's menu playlists (at most 2 GB a disc) where the stubs can't decide. `check` runs `generic.keys` (`wait menu`, right, down, ok, `wait playlist any`) on every disc in our player (`tests/bdj/replay-player.ts`) and in libbluray (`tools/bdj-trace`), compares settled planes and the calls that start something, and gives each disc a verdict: `works`, `unconfirmed` (agrees with libbluray, but a key step was never compared and ours showed no reaction: for a check by hand), `libbluray-fails-too`, `missing-class`, `unsupported-video`, `stall`, `diverges` or `error`. It is incremental (a run is reused while the disc, the code and the script are unchanged; `--only <id>`, `--force`, `--ours-only`, `--no-run`), names discs only by a hashed id and writes `results/` and `summary.md` under `$BDJ_LIBRARY_DIR`; its `map.tsv` (id to NAS path) never goes into the repo. A full check of the 166 discs takes about 80 minutes; run it under `caffeinate -i` (a replay the Mac slept through is voided).
- `npm run disc-server -- --root <dir> [--root <dir>] [--cert <pem> --key <pem>] [--port 8443]`: the development disc server (`tools/disc-server/`, README there). It serves disc folders and the built player (`dist/`, so run `npm run build` first) from one origin with COOP/COEP, and speaks the NAS server's disc API (library listing, manifest with inlined metadata, range reads), so a disc opens through the same `RemoteSource` as a NAS disc. It answers only loopback and LAN addresses and needs a token that is new on every run; without `--cert`/`--key` (mkcert) it speaks plain HTTP on 127.0.0.1 only.
- `tools/devices/` (README there): device automation over W3C WebDriver. `run.ts` opens a URL, waits, taps, screenshots and collects telemetry; `probe.ts` runs the probe page against a disc on the disc server; `gate.ts` is the 5d device gate (start-up, a disc's key script against libbluray's settled plane hashes, ten minutes in the menu, latency and memory); `live-check.ts` is the 5e live check, on a preview origin only, against the live NAS: two made-up test people with two devices each, BD-J saved data that follows a person and never crosses to another (`disc-bdj-store`, copied onto the NAS for the run and removed after), and the library discs the library check left unconfirmed, opened and screenshotted; with `--places`, a generated 60 s disc placed beside it checks resume on the phone (a pause saved at the stopped clock, Resume with a stored subtitle back, Continue watching), and the test subtitle is deleted after; it deletes the test people at the end, even on failure. Targets: the iOS Simulator through Appium (`sim:<name>`), a real iPhone or iPad through plain `safaridriver` (`ios:<udid>`), Mac Safari through `safaridriver` (`safari`), and installed Chrome and Firefox through Playwright (`chrome`, `--touch` for Pixel 7 emulation, `firefox`). Results (JSON and screenshots) go to `--out`, by default a gitignored folder, and never hold the token.
- `npm run server:build` bundles the NAS server (`server/`) into `server/dist/server.mjs`; `npm run server:dev` builds it and serves `fixtures/synthetic` as root `syn` on port 4192 (data in `.cache/server-data`). `npm run server:deploy` (`server/deploy/deploy.sh`, the owner's deploy) builds the image for linux/amd64, ships it to the NAS over ssh, writes the generic compose files, restarts the service and adds the `/bluray/*` route to Caddy; the ssh host and Caddy site come from `BLURAY_NAS_HOST` and `BLURAY_CADDY_SITE` in the environment or the gitignored `.env.local` at the repo root, and the NAS's own `.env` and `compose.override.yaml` are never written. A deploy refuses while the NAS's `.env` has no `PUBLIC_BASE`. `server/deploy/deploy.sh --owner-code [--person <name>]` deploys nothing and prints a fresh owner pairing code (for the first owner person, or the named owner person, made if needed) with its link and a terminal QR. `server/deploy/deploy.sh --nas-id` deploys nothing and prints the NAS's rendezvous id (`node server.mjs nas-id`, its key's thumbprint), the value for the Worker's `NAS_IDS` and `TURN_NAS_IDS`. Others self-host from the published image `ghcr.io/brianhvo02/bluray-server` (CI's `publish-server-image` job, linux/amd64, tagged `latest` and the short commit) with the generic `server/deploy/compose.yaml` and `.env.example`; see `docs/self-hosting.md`, and spec `docs/superpowers/specs/2026-10-22-self-hosting-design.md`.
- `npm run seikou-encode -- plan <disc> [--playlist ID]` and `npm run seikou-encode -- encode <disc> --playlist ID --episodes SPEC --out DIR` run the encoder (`encoder/`), which cuts a decrypted disc's playlist into episodes at chapters and encodes AV1 (SVT-AV1) and Opus into MKV through pipes, with no intermediate files. `encode` reads the record the subtitle helper saved for the disc and playlist (it must match the playlist and `--episodes`, else exit 2; `--no-subtitles` ignores it) and puts in the MKV every ticked audio stream as its own Opus track, the ASS tracks retimed as previewed, their fonts as attachments, the disc's PGS tracks (`--no-pgs` leaves them out), and the record's titles, names, languages and defaults; `--web DIR` also packages each episode into `DIR/<name>/`, and `npm run seikou-encode -- package <episode.mkv> --out DIR` packages an existing MKV (no re-encode): `video.webm` (AV1 and Opus), `subs/*.ass`, `fonts/`, `pgs/*.sup`, `chapters.vtt` and `episode.json`. `--cache DIR` moves BestSource's index files. The encoder pairs with Seikou's NAS as an owner device (`npm run seikou-encode -- nas pair (--code CODE --base URL | --link URL)`, `nas status` and `nas unpair`, or the app's Settings; `<data>/nas.json`, mode 0600, holds the device key, never a session token) and then reads the NAS's discs through its API, never SMB or ssh: `<disc>` may be `nas:<disc key>`, mirrored into `<data>/fetch/<disc key>/` (metadata whole, clips as sparse files of their true size holding only what was fetched, recorded in `fetch.json`; the listing is kept in `<data>/nas-library.json`), with an episode's clips fetched before it is encoded and let go of after. `--nas` uploads each episode to the NAS's Encodes library in place of `--out` (resumable, through `<data>/nas-out/`, deleted here once the NAS has filed it) and needs every episode's title (AniList, TMDB season or film, or own) and number, which the app's Episodes page saves with the chapter names in `<data>/chapters/<disc key>/<playlist>.json` and the encode writes as chapter titles and the tags `ANILIST_ID` (AniList titles; else `SEIKOU_TITLE` and `SEASON`), `EPISODE`, `EPISODE_TITLE`, `SEIKOU_DISC_KEY`, `SEIKOU_PLAYLIST`, `SEIKOU_EPISODE_START_MS` and `ENCODER`. An `encode` of a NAS disc holds `<data>/jobs.lock` for its run. It needs VapourSynth with BestSource, SvtAv1EncApp and opusenc; its tests (`npx vitest run --project encoder`) skip what needs a missing tool. See `encoder/README.md`.
  - `npm run seikou-encode -- serve <disc> --playlist ID --episodes SPEC [--port N] [--no-open]` starts the subtitle helper on 127.0.0.1 and prints `Helper: http://127.0.0.1:<port>/helper/<session id>?t=<token>` (a new token every run): the user picks the show on AniList and a fansub release (SeaDex, an Anime Tosho search or their own files), matches files to episodes, lines each episode up against the disc's audio and previews it in Seikou's engine with a nudge, sets names and languages, and saves the record the encode will read (`<data>/subtitles/<disc key>/<playlist>.json`; the data directory is Application Support on macOS, `$XDG_DATA_HOME` elsewhere, `SEIKOU_ENCODE_DATA` overrides it). `SEIKOU_ENCODE_FIXTURE=<dir>` reads recorded SeaDex, Anime Tosho and AniList answers instead of the network (tests only; `encoder/tests/fixtures/fansubs`). Without `vspipe` and BestSource it still starts and previews at the release's own timing.
  - `npm run seikou-encode -- app [--root DIR]… [--port N] [--no-open]` starts the encoder app on 127.0.0.1 and prints `App: http://127.0.0.1:<port>/?t=<token>`: a library of the discs under the saved folders and the `--root` folders (while paired, also By show), a disc's playlists, chapters grouped into episodes while the playlist plays, the subtitle helper per grouping, settings profiles, an encode queue that keeps running when the page is closed (jobs, logs and test samples in the data directory) and test encodes that compare profiles on short samples. It needs the built page like `serve`. One process runs a data directory's queue, holding `<data>/jobs.lock` (its pid; a lock whose process is gone is taken over): a second `app` on the same data directory refuses to start with one line, and a `serve` beside an `app` runs no queue, its queue routes answering 409 `queue-elsewhere`. The suggested output folder is `<data>/output/<disc label>-<8 hex of the disc key>/<playlist>`, and a job whose folder and file names meet another queued job's is refused with 409 `output-in-use`, except a re-encode of the same disc, playlist and episodes, which is queued with a warning. While paired, the library lists the NAS's discs too (marked NAS) and opens **By show** (spec `encoder/docs/superpowers/specs/2026-11-10-library-by-show-design.md`; By folder and This Mac remain): the NAS's shows from its title library (`GET /api/nas/shows`, a show's seasons and discs from `shows/<id>`, posters through `/api/nas/art/<id>`), a season disc by disc with each episode Encoded (in the NAS's Encodes library), Queued (a NAS job here already encodes it) or To encode, **Check episodes** per disc, and **Queue N episodes to the NAS** for what the season has left, a batch of one job per checked playlist, each with `only` naming the episodes still to encode (mapped by title and number from whichever playlist the NAS lists them on), disabled until every disc with episodes to encode is checked and while the NAS hasn't said which episodes its Encodes library holds. A disc is checked on its Episodes page, prefilled from the NAS's match (episode titles may be AniList, TMDB season or film, or an own title the owner adds by hand on the NAS, found through the NAS's `admin/lookup` one lookup at a time), with **Mark checked** (`POST /api/discs/<key>/playlists/<id>/check`; 409 `needs-title` while an episode lacks a title, 409 `record-mismatch` when the saved subtitle record groups the chapters otherwise), which is the one place the encoder writes the NAS's library: when all of a disc's episodes are under one title that differs from the NAS's match, it files the disc under it (an AniList entry that is a season of a series as that series and season number, with no disc number, as the NAS's `admin/anilist-place` answers it through the same one-at-a-time line as the lookups, even for a season the NAS holds no disc of; a NAS from before that route is searched in its catalogue instead; an AniList entry AniList doesn't know, one the NAS can't number (a fork in its chain) or one an older NAS's catalogue doesn't hold is left alone, answered `failed`, unless the catalogue holds its season). A job can send its episodes to the NAS (`settings.destination: 'nas'`): it fetches one episode ahead, encodes, uploads, deletes once the NAS confirms, and shows "Waiting for the NAS" while the NAS doesn't answer; queuing it answers 409 `nas-not-paired`, `nas-needs-title`, `nas-duplicate-episodes` or `nas-encodes-off`, and a test encode of a NAS disc 409 `nas-test-unsupported`.
  - `npm run encoder:web:build` builds the helper page into `encoder/web/dist`, which `serve` needs (`SEIKOU_ENCODE_WEB_DIR` points at another folder); `npm run encoder:web:dev` serves it with hot reload against a running `serve` named by `SEIKOU_ENCODE_API`.
  - `npx playwright test -c playwright.encoder.config.ts` is the encoder's end-to-end check in installed Chrome, in three projects. `helper` (`encoder/tests/e2e/helper.spec.ts`): its `webServer` builds the page and runs `serve` over `encoder/fixtures/disc-speech` on port 4195 with the recorded answers and a temporary data directory, reads the address with its token from the output, and is never reused. `app` (`encoder/tests/e2e/app.spec.ts`): a second `webServer` runs `app --root <temporary library of copies of disc-speech and disc1>` on port 4197 with its own data directory, and the test walks the library, episode grouping, helper, a queued encode with progress and MKVs, cancel and a test encode. `nas` (`encoder/tests/e2e/nas.spec.ts`, two serial tests): `encoder/tests/e2e/nas-stand-in.ts` runs `npm run server:build` and the NAS server on port 4198 over a temporary copy of `fixtures/synthetic` (an empty `ENCODES_DIR`, the made-up AniList and TMDB entries of `encoder/tests/fixtures/nas-titles.json` plus Starfall Wanderer, no rendezvous) with copies of the encoder's `disc1` and Seikou's `disc-vm` filed under the made-up series Lantern Road and the encoder's speech disc under Starfall Wanderer, and a fourth `webServer` runs `app` on port 4199 with its own data directory. The first test mints an owner code with `server.mjs owner-code`, pairs on Settings, opens the Library by show, finds Lantern Road, checks its second disc (prefilled from the NAS) under a TMDB series, and sees the NAS file the disc there. The second opens Starfall Wanderer's season, groups the speech disc into two episodes (chapter 1 named Opening), picks the title through the NAS's lookup, marks the disc checked, queues the season's two episodes to the NAS, and checks the job's log, that the NAS lists both and holds the chapter title, that the season shows both Encoded, that `nas-out/` is empty and that the mirror holds no whole clip. The line-up and encode steps need VapourSynth with BestSource, SvtAv1EncApp and opusenc and are skipped, with a reason, without them. A global teardown removes the temporary folders.
- `npx tsx scripts/verify-level.ts --base <NAS API base> --code <owner code> --level <level> (--disc <id>... | --pick h264|mpeg2|vc1|uhd) [--audio <n>] [--parallel <n>] [--max-mb <n>]` checks a quality level against a running NAS server, reading as the app does. ## Architecture

Packages: everything that is not specific to the app lives in eight npm workspace packages under `packages/`, imported as `@seikou/<name>`. They ship TypeScript sources (no build step) and are unpublished; a project outside the repo installs them as `file:` dependencies, which `npm run package-smoke` (`scripts/package-smoke.sh`, run by CI) checks in a temporary project. Each has a one-paragraph README and its own NOTICE.
- `bdmv`: the disc format: `index.bdmv`, `.mpls`, `.clpi`, movie object, BDJO, `sound.bdmv` and `id.bdmv` parsers ported from libbluray, the UDF reader for ISOs (from libudfread), the M2TS demuxer (`demux/`) and the H.264/HEVC parameter-set readers (`codecs/`).
- `pg`: PG subtitles (segment decoder, renderer, `OverlayPlane`), ported from libbluray.
- `ass`: the ASS renderer, ported from libass, with the DejaVu fallback font.
- `engine`: the player engine (worker, `Player`, navigation, HDMV VM, IG menus, decode, render, shaders, SRT and the subtitle set) and the page-side `PlayerController`; FFmpeg's `audio.wasm` is in `packages/engine/wasm/audio/`. `openDisc`, `createController({ worker, profile, exposeTelemetry? })` and `createEngineWorker(name)` are its entry points.
- `nas`: the wire contract shared by the server, the app and the rendezvous Worker (API types, disc keys, content hash, place rules, pairing codes, CORS policy, WebRTC framing).
- `titles`: library naming and metadata (folder-name parsing, AniList, TMDB, Discogs, MusicBrainz, TheDiscDB, matching, the catalogue, owner choices).
- `fansubs`: finding, fetching and timing fansub subtitles.
- `matroska`: Matroska and WebM writing and reading for any host (no `node:`, no `Buffer`): `writeMatroska` through an `MkvSink`, `readMatroska` through a `RangeReader`; the encoder's `mux/mkv-file.ts` wraps them on files.

The packages leave three things to their host, so none of them needs the app: BD-J is an optional `BdjProvider` (`PlayerDeps.bdj`, `packages/engine/src/bdj-provider.ts`), which the app implements as `seikouBdjProvider` in `src/bdj/provider.ts`; the PG renderer takes `PgRendererDeps { displayFlag(); onOverlay(op) }` instead of the register file; and `@seikou/fansubs` takes an injected `AudioDecoder`, which the server backs with ffmpeg (`ffmpegAudioDecoder`, `server/src/fansubs/ffmpeg-decoder.ts`), so no package runs ffmpeg. BD-J itself (`src/bdj/`) stays in the app, with the class library it needs; `src/engine-worker.ts` is the app's engine worker entry, which passes the provider.

The encoder (`encoder/`) is an application like `server/`: it uses `@seikou/bdmv` to read playlists, clips and streams, runs VapourSynth (BestSource), SvtAv1EncApp and opusenc as child processes joined by pipes, and writes Matroska itself (`@seikou/matroska`, with the AV1, Opus and ASS pieces in `encoder/src/mux/`), so it needs no ffmpeg. Each audio stream is chosen by PID (`encoder/src/plan/audio-streams.ts`) and found through the clip's PMT (`encoder/src/disc/pmt.ts`), and its decoded channels and rate are checked against the playlist's STN attributes once decoding starts; PGS streams pass through from the disc; `encoder/src/package/` turns an episode MKV into the static web directory (WebM remux, ASS and PGS as files, WebVTT chapters, the manifest). The app (`seikou-encode app`) has two halves: `encoder/src/server/` is its local backend (token and Host checks; the disc library under the roots; playlists and chapters; helper sessions, each a disc, playlist and episode list; settings profiles; the encode queue in `jobs.json` and its runner, one job at a time, under the data directory's lock; AniList, SeaDex and Anime Tosho through `@seikou/titles` and `@seikou/fansubs`; lining up on the disc's audio decoded by BestSource; the disc's files for the engine; the saved record), and `encoder/web/` is the page (React, Vite, its own wire types in `api-types.ts`): the library, episode grouping while the playlist plays in `@seikou/engine`, settings, the queue and test encodes, and the subtitle helper as one of its pages, which plays the disc with the retimed ASS and the release's fonts. `serve` runs the same backend with one helper session. Its type-check projects are `tsconfig.encoder.json` and `tsconfig.encoder-web.json` (the page); its tests are the `encoder` Vitest project, and the page's end-to-end check is `playwright.encoder.config.ts`.

There are three execution contexts, and a fourth (the BD-J worker, below) while a BD-J title runs. They communicate only through typed messages and one shared buffer.

1. **Main thread** (`src/ui/`, with the controller in `packages/engine/src/controller/`): React UI. `PlayerController` is an external store over the worker protocol, read with `useSyncExternalStore`. There is no state library. `reduceEvent` is a pure reducer from `EngineEvent` to `PlayerSnapshot`, and it is unit-tested. `create-controller.ts` starts the worker. `?telemetry=1` copies telemetry to `window.__blurayTelemetry`, which is what the E2E tests read (its `bdj` field holds BD-J start-up times since the open and `inputLatencyMs`, the BD-J menu responsiveness). `?bdjfail=1` is test-only: the engine worker gets an unreadable class library, so BD-J fallback can be tested in the browser. `?nodecoder=1` is test-only too: the engine sees no supported video decoder configuration, so a decoder that fails to configure can be tested in any browser. `?noav1=1` is test-only: the AV1 check (`av1Playable` in `src/ui/video-caps.ts`, read once as the app loads) says unsupported, so an encode's pre-flight shows its AV1 warning in any browser. `?rtcrelayed=1` is test-only: `RtcConnection.relayed` is true, so the player's "Relayed" badge shows without a relay. `?bufferask=1` is test-only: the NAS pre-flight asks before any buffer-first wait (it never buffers silently), so its Wait screen can be tested with the short synthetic discs. `?touchlog=1` is test-only: a box over the page lists the last touch, pointer and click events and the alphabet bar keys picked (`src/ui/TouchLog.tsx`), for debugging a phone without Web Inspector. `?nonestedworkers=1` is test-only too: the engine worker acts as if it could not start workers, so the BD-J capability message and the picker can be tested. `?placemin=<seconds>` is test-only: the length that makes a playlist worth a saved place (default 300 s), so the short synthetic discs can save places.
2. **Engine worker** (`packages/engine/src/`, framework-free; the app's entry is `src/engine-worker.ts`, the package's own `worker.ts`, both calling `startEngineWorker` in `worker-main.ts`): `Player` owns one disc and at most one playing playlist (a `Session`). The `<canvas>` is transferred as an `OffscreenCanvas`, so presentation timing doesn't depend on React.
3. **AudioWorklet** (`packages/engine/src/controller/pcm-worklet.ts`): plays PCM from a `SharedArrayBuffer` ring (`packages/engine/src/audio/ring.ts`) and atomically publishes the count of frames played. `MasterClock` derives playback time from that count, falling back to the wall clock when no audio is playable. Video frames are presented against this clock.

`packages/engine/src/protocol.ts` is the contract between the UI and the engine. It defines the `EngineCommand` and `EngineEvent` discriminated unions and `Telemetry`. Change it first when you add a feature that crosses the boundary.

Data flow inside the engine (paths relative to `packages/engine/src/` unless named):
- `disc/`: `ByteSource` and `FileSource` (a normalized `path → Blob` map, so the engine never sees file handles). `open-disc.ts` loads index, playlists and clips and maps failures to `DiscError` codes. `ByteSource.read` takes an `AbortSignal`; the optional `ByteSource.peek` reads a range with no read-ahead (`RemoteSource`: exactly the range when no chunk holds it), which the encryption check (`checkStreamReadable`) uses so opening a NAS disc doesn't stream its main clip ahead of BD-J's reads.
- `@seikou/bdmv`: `index.bdmv`, `.mpls` and `.clpi` parsers, ported from libbluray.
- `nav/timeline.ts`: maps play items onto one continuous playlist time, handling the 33-bit PTS wrap and per-item discontinuities. Seeks go through the EP map to an SPN, then to an aligned byte offset.
- `@seikou/bdmv`'s `demux/` (192-byte source packets, then TS, then PES) feeds `playback/pipeline.ts`, which runs read-ahead, backpressure and cancellation of abandoned reads on a seek.
- `decode/`: `WebCodecsVideoDecoder` (Annex-B; the codec string comes from the SPS in `@seikou/bdmv`'s `codecs/h264.ts`/`hevc.ts`) and `lpcm.ts`. Audio goes PES → `AudioFramer` (`audio-frames.ts`) → `WasmFrameDecoder` (`wasm-audio.ts`, or LPCM) → `PcmChunk` → `AudioWriter`; decoders come from `PlayerDeps.createAudioDecoder`, and TrueHD is reduced to its AC-3 core by `TrueHdCoreFilter` first. `render/`: `VideoPresenter` (chooses which frame to show against the clock) and `Compositor`. A playlist whose video coding the player can't decode (MPEG-2, VC-1: `isSupportedVideoCoding`) still plays, without a picture (5e, ruling R12): audio, subtitles and IG or BD-J graphics over black at 1920×1080 on the audio clock (the wall clock when nothing is audible), its reads paced by the clock through the clip's EP map (R8, R10), ending at EOF once what was delivered has played (R11). The `unsupported` event with `noPicture` shows the notice once per disc and clears it when a playlist with a picture starts (R9). `UnsupportedCodecError` remains for a decoder that fails to configure.

Subtitles: `nav/subtitles.ts` (`PgStreamControl`) follows PSR2 on the navigator's registers (or private ones on discs without a navigator), decodes the PG PID the pipeline reads (`@seikou/pg`'s `PgSegmentDecoder`) and renders display sets at their PTS into a double-buffered PG `OverlayPlane` (`PgRenderer`, whose `displayFlag()` reads PSR2); SRT is decoded, parsed and laid out by original code in `subs/`; the compositor draws video, PG, text, then IG.

ASS (`@seikou/ass`, `packages/ass/src/`): ported from libass 0.17.5 function by function: `parse.ts` (script and `[Fonts]`), `fonts.ts`/`font-tables.ts` (matching from the sfnt tables, faces registered as `FontFace`s; a family nothing supplied falls back to the device's installed font through CSS `local()`, measured by the browser, in `device-fonts.ts`, an addition to the port that the engine turns on with `AssFonts`'s `deviceFonts` option and the libass comparison leaves off), `tags.ts`/`state.ts`/`events.ts` (override tags and `\t`), `layout.ts` (advances from the browser's `measureText` through `GlyphMeasurer`, wrapping, alignment), `transform.ts`, `collisions.ts`, `frame.ts` (one frame's events and matrices); `raster.ts` draws runs with Canvas2D (glyph masks supersampled and box-filtered in JS, libass's compositing and blur, mask and layer LRUs) and `renderer.ts` (`AssRenderer`, a `TextRendererLike`) caches static events. `tests/ass-trace/` compares it with patched libass; a divergence is a porting bug, as with vm-trace. The engine's `subs/text-set.ts` holds the episode subtitle set: several SRT/ASS files, each placed at a playlist time (auto-placed on play items of 5 minutes or more) with its own offset.

Menus: `nav/navigator.ts` owns the HDMV VM (`hdmv/`), the register file and the graphics controller (`graphics/`) and drives the `Player` through a narrow `PlaybackPort`; IG units are queued by PTS (sub-path IG is preloaded whole) and the controller's overlay operations update an `OverlayPlane` that the compositor draws over the video. All of it is ported function by function from libbluray at commit `448f896` (`scripts/fetch-libbluray.sh` puts the source in `.cache/libbluray`); `tests/vm-trace/` compares our VM, navigator and graphics against patched libbluray traces, and a divergence is a porting bug to fix in the port, never in a golden file.

Shaders: `shaders/` in the engine parses mpv user shaders (`parse.ts`, `rpn.ts`), plans a frame's passes (`plan.ts`) and runs them on WebGL2 in the worker (`webgl-backend.ts`); `ShaderStage` (driven by the `setVideoShaders` command and `shaderStatus` event) sits between the decoder and the compositor, so the shader output replaces the video frame. The UI side is `src/ui/shader-sets.ts` (the 12 built-in Anime4K sets and `input.conf` imports), `src/ui/shader-library.ts` (IndexedDB), `src/ui/shader-model.ts` and the Shaders menu, and `v` cycles sets. Anime4K's 14 shaders ship with the app in `src/ui/anime4k/shaders/` (release v4.0.1, README there): `src/ui/bundled-shaders.ts` gives the model their build asset URLs, a set's files are fetched the first time it is applied (an imported file of the same name wins), and `src/sw.ts` keeps them in a runtime cache rather than the precache. `fixtures/shaders/` holds test copies.

BD-J (`src/bdj/`, in the app, milestone 5b): a JVM in TypeScript that runs libbluray's Java stack. `jvm/` holds the class-file parser, zip reader, loader, heap, interpreter, green threads (`threads`), the virtual file system (`vfs`) and `natives/`; `host.ts` has the `BdjHost` interface and `RecordingHost`; `runtime.ts` (`BdjRuntime`) is ported from libbluray's `bdj.c`. `tests/bdj/conformance` runs small Java programs and compares their output with HotSpot's; `tests/bdj/` also holds the control-call trace comparison and the synthetic BD-J disc.

BD-J playback (`src/bdj/`, milestone 5c) adds a fourth execution context, the BD-J worker (`bdj-worker.ts`, entry `bdj-worker-entry.ts`), started by the engine worker once per BD-J entry. The register file is shared with it through a `SharedArrayBuffer` (`shared-registers.ts`), and a status block (`status-block.ts`) carries playback time and the UO mask. `BdjSession` (engine side) routes Java's calls to `PlayerBdjHost` (`player-host.ts`), which drives the `Player`; playback PSR updates are shared with the Navigator (the engine's `nav/playback-psrs.ts`); events for Java come from `events.ts`. The HDMV Navigator is dropped while BD-J runs. BD-J reaches the player only as an optional provider, `PlayerDeps.bdj` (`packages/engine/src/bdj-provider.ts`: the worker, class library, host, session, plane, status block and input helpers, typed against the engine's own `bdj-types.ts`; `src/bdj/provider.ts` assembles Seikou's `seikouBdjProvider` and `src/engine-worker.ts` passes it; no engine file names a BD-J directory, which `packages/engine/src/no-bdj.test.ts` guards). Without a provider a BD-J disc or title opens to the picker with the `bdj` notice naming the missing `BD-J runtime`. `PlayerDeps` also gains `setTimer`, `playerSettings` and `bdjLog`. A failed boot falls back to the title picker at once; only a hang waits for the start-up timeout: 20 s of active time from the boot (once the class library has arrived) to Java's first `selectPlaylist`, first visible plane (a menu) or first background still (ruling R7 in 5d). It counts only while the page is visible and the host awake (`session.ts`, 1 s ticks; a tick 5 s late restarts the 20 s; 5e ruling R22), and not while the BD-J worker waits on its own reads (JARs, resources, storage scopes, FreeType: the worker's `io` messages), for at most 120 s per boot (`IO_PAUSE_CEILING_MS`, 5e ruling R26). The player settings (`playerSettings`, from the browser's locale) are written to the registers when a disc whose index names a BD-J object opens, as libbluray does at `bd_open`, so a mixed disc's HDMV First Play reads them too; discs without BD-J keep the registers' defaults. Telemetry has `bdj { bootMs, firstPlaylistMs, firstFrameMs }`. What discs save under `/persistent/` and `/buda/` lasts between viewings through `src/bdj/store/` (5e): `scopes.ts` derives the scopes (`persistent/<orgId>`, `buda/<orgId>/<discId>`, and `buda/<orgId>` for the files beside the disc folders) from the BDJOs and `id.bdmv` as libbluray does, `ScopeSync` (in the BD-J worker) loads them into the VFS before `Libbluray.init` and saves a scope whole after its last write (2 s; 100 ms for the browser's store, because Chrome and Safari drop IndexedDB work started during pagehide), on `flushSaves` (pagehide) and on stop (the engine waits for the worker's `stopped`), and `IdbBdjStore` keeps a picked folder's in IndexedDB (source `local`). A disc opened from a server goes through `NasDiscStore` (`nas-store.ts`, chosen in the BD-J worker): it asks `GET me` whose device this is, then keeps each scope in that person's NAS store (`NasBdjStore`: ustar snapshots from `tar.ts`, quoted ETags with `If-Match`/`If-None-Match: *`, a 412 merged per file by mtime, a 507 a full disk for Java through `ScopeSync.full`, a 503 retried) behind a write-ahead copy in IndexedDB (`WriteAheadNasStore`, ruling R17: saved 100 ms after a write as `nas-person:<personId>`, marked pending, put on the NAS 2 s later, on flush, on stop and when the page is shown again; a pending copy is merged and put at the next boot). A NAS boot gives the store 12 s (`BdjStore.loadTimeoutMs`, ruling R28): a scope the NAS misses with no copy here starts empty and its writes are kept as a pending copy marked `unmerged`, merged at the next boot with the NAS's files winning on every path both have (ruling R29); when `GET me` misses, the session starts empty and only adds to `nas-unconfirmed:<apiBase>#<personId>`, kept for the person this device was last confirmed as (`nas-device`), merged in only when the NAS names that person again and removed when it names someone else or after 30 days (ruling R30). A put that took files from the NAS folds them into the write-ahead copy whatever was saved meanwhile. Records from before (`nas:<discId>`) move into the person's scopes once and are removed only after the NAS has them; a server with no people (the dev disc server) keeps them in this browser as `nas:<discId>`. Every NAS write carries `X-Bdj-Person` (the NAS answers 409 `person-changed` once the device belongs to someone else, and the copy stays pending under its own person), and `GET me` is asked again before each put. A disc without a disc ID keeps its BUDA scope under a fingerprint of its BDMV files (`discFingerprint`; Java still sees libbluray's 32 zeros). 16 MB per scope, counted as the NAS counts it (the ustar archive, headers and padding included; ruling R24), so the write that would cross it is an `IOException` in Java at once; 256 MB per person on the NAS, which a later 507 reports. When saves won't last (a write into a scope kept in memory only with no copy, a write refused for room, a NAS put refused for good) the BD-J worker sends `storageLost` once and the player shows the `bdj-storage` notice once per disc open (ruling R32; not for a missed boot that keeps an unmerged copy, a merged 412 or a put still retried).

BD-J menus (`src/bdj/`, milestone 5d):
- **Graphics plane** (`graphics-plane.ts`): `updateGraphicN` and libbluray's ARGB overlay (init, draw, flush, close) are ported onto a shared 1920×1080 ARGB `SharedArrayBuffer` with an Atomics header (lock, size, dirty union, flush counter). The BD-J worker writes the dirty rectangle under the lock; the engine worker's `GraphicsPlaneReader` only try-locks (never `Atomics.wait`), and the compositor draws the plane where IG goes (over video and subtitles), scaled to the video rectangle, at the next presented frame after a flush. It is cleared and released when BD-J stops, a playlist is picked from the picker or the disc closes.
- **Background stills** (`background.ts`, `jvm/natives/havi.ts`): libbluray never draws `HStillImageBackgroundConfiguration.displayImage`; we do, under the video, decoded by the browser (`createImageBitmap`), because Java never sees those pixels.
- **Fonts**: FreeType 2.13.2 compiled to WASM (`src/wasm/freetype/`, `fonts/freetype.ts`) under ports of libbluray's `java_awt_BDFontMetrics.c` and `java_awt_BDGraphics.c` natives (`jvm/natives/fonts.ts`). FreeType is fetched on the first font use, not at boot, and a failed load is remembered for the session. Disc fonts come from `dvb.fontindex`; the JRE's logical font files resolve to the bundled `packages/ass/src/default-font.ttf`, as in the libbluray harness (`fonts/system-fonts.ts`).
- **Input** (`input.ts`): keys go to Java as `bd_user_input` sends them (UO checks, no key-interest filter; Escape/Back is not sent, ruling R5), clicks and taps as `bd_mouse_select` plus the activate key, pointer moves as mouse events, through a bounded event queue. While the plane shows any pixel a tap or click goes to the disc; on an empty plane it toggles the controls. A tap with no reaction (plane flush, control call or still) within `bdjTapWindowMs` (0.2 s, constrained 0.5 s) counts as ignored: the on-screen remote opens once per menu with a notice. `InputLatency` measures input to the presented plane change.
- **Control bar and touch over a disc menu (HDMV and BD-J, rulings R9, R11–R15):** empty bar space passes clicks through; in a menu a pointer move wakes the bar only near the bottom edge and it hides as the pointer returns to the picture; keys that go to the disc don't wake it. On touch, a tap on the picture goes to the disc; a tap off the picture (letterbox or pillarbox), an HDMV tap that hits no button, a BD-J tap Java ignores, or a long press (≥ 500 ms, ≤ 10 px) shows the controls and is never sent to the disc (`src/ui/touch.ts`, `PlayerScreen.tsx`).
- **Memory** (`memory-profile.ts`): `bdjClassCacheBytes`, `bdjVfsCacheBytes` (desktop unlimited, constrained 64 MB; a write past it fails as a full disk, ruling R16), `bdjDecodedImageBytes` and `bdjTapWindowMs`. Telemetry adds `bdjPlane { flushes, tapsIgnored, hash }`, `bdjMemory` (JVM class bytes, VFS, plane, stills, FreeType; sampled coarsely) and `bdj.inputLatencyMs { last, max, count }`.
- **Boot stalls**: at the 20 s start-up timeout the session asks the BD-J worker for a thread dump of every Java thread (`jvm/threads.ts`), logs it, and ignores everything else Java sends from then on.
- **Disc reads**: on a NAS or disc-server disc the BD-J worker builds its own `RemoteSource` with a small read-ahead (`bdjRemoteReadAheadBytes`, 16 MB desktop, 8 MB constrained, ruling R20), since it reads JARs and metadata, not streams.

`tests/bdj/` adds key scripts (`scripts/*.keys`) whose goldens hold libbluray's control calls and settled plane hashes, the synthetic menu disc (`disc-bdj-menu`: text in a CFF disc font, a PNG logo, buttons, a still) and committed local-disc goldens (`golden/local/`, hashes only) for `tests/local/bdj-menus.test.ts`.

Cross-browser: `src/ui/capabilities.ts` builds the capability report that gates features per browser (no user-agent sniffing, except the iPadOS check below). The memory profile (`packages/engine/src/memory-profile.ts`, chosen by `src/ui/memory-profile.ts`, forced with `?memory=desktop|constrained`) reaches the engine as the `setMemoryProfile` command and sets the IG sub-path preload limit, the ASS cache budgets and text supersampling cap, and the decoded-frame queue length; the constrained profile skips IG sub-paths over 64 MB. `packages/engine/src/controller/platform-session.ts` holds Wake Lock and Media Session, `src/ui/touch.ts` the touch gestures, and a fullscreen adapter (with an Add-to-Home-Screen hint on iPhone) replaces element fullscreen where it is missing. The service worker is `src/sw.ts` (vite-plugin-pwa `injectManifest`, `tsconfig.sw.json`): production-only registration, COOP/COEP re-added to cached responses, network-first navigation with a 3 s timeout, `probe.html` excluded.

NAS server (`server/`, milestone steps 2–4, bundled by `server/build.mjs`, run in Docker by `server/deploy/`): a Node server with no native dependencies. Settings come from the environment (`config.ts`; `server/deploy/.env.example` lists them): `PUBLIC_BASE` is required (the server and every subcommand refuse to start without it), `APP_URL` (default the hosted player) is what pairing links open, `LOOKUP_CONTACT` (printable ASCII) is added to the MusicBrainz and Discogs User-Agent, and an empty `TRUSTED_PROXY` trusts no proxy. `library.ts` scans the roots (`LIBRARY_ROOTS`, `name=dir` or `name=dir@group`; roots sharing a group show as one top-level folder) up to six levels deep, slowly (`SCAN_PAUSE_MS`) and nightly; a disc whose files changed within `SETTLE_MS` (an hour) is still downloading and is left out; `.iso` files are read through the UDF reader (`iso.ts`); a root whose folder is missing or empty keeps the discs of its last scan, and `Library.drives()`/`forget(name)` list the roots and drop the kept discs of one the last scan didn't find (`GET admin/drives`, `POST admin/drives/<name>/forget`: 409 `drive-present` or `scanning`; NAS settings' **Drives**, `DrivesSection.tsx`). Each new or changed disc yields evidence (`server/src/titles/evidence.ts`: `bdmt` names, path segments, catalogue-number-like tokens, the TheDiscDB content fingerprint, main playlist durations and chapter counts). `packages/titles/src/match.ts` groups discs by parent folder, parses names (`parse-name.ts`), looks them up on AniList (`anilist.ts`, paced), TMDB (`tmdb.ts`, only with `TMDB_API_KEY`) and the bundled TheDiscDB index (`discdb.ts`), all in `@seikou/titles`, and files a disc only under cautious acceptance (one entry fits, two pieces of evidence agree or one exact match stands alone, the season or movie is resolved, the disc's place is known); everything else goes to Unsorted with a reason the owner sees. `packages/titles/src/episodes.ts` guesses episode lists from playlist lengths and answers null when unsure. `packages/titles/src/catalogue.ts` builds titles, seasons, disc slots, episodes, extras, Music, Unsorted and Hidden from matches, metadata and owner choices, with no network access. `packages/titles/src/owner-store.ts` keeps the owner's choices, own titles and gate in `owner.json`; choices are keyed by disc id but carry the disc's fingerprint, so a moved disc gets its choice back. `server/src/titles/service.ts` matches after each scan, writes checkpoints so a long run resumes, keeps `metadata.json` so a restart serves the last catalogue offline, and refreshes on a schedule (Unsorted weekly, entries monthly); `packages/titles/src/art.ts` caches posters within a byte budget. Routes (`routes/`): `pair.ts` (codes, sessions), `discs.ts` (manifests and range reads), `library.ts` (folders), `titles.ts` (`me`, titles, art), `admin.ts` (owner screens' actions; `GET admin/anilist-place/<anilistId>` answers `{ titleId, season, name }`, where an owner's choice files a disc under an AniList entry (a TV entry's series and its season in the chain, any other entry as its own title with no season) whether or not a disc of it is filed, fetching the entry and its chain under the lookups' per-device limits and timeout; 404 `not-found`, 409 `no-season` when the chain can't number it or another member shares its number, 503 `source-unreachable`) and `bdj-store.ts` (each person's BD-J saved data); every route needs the device token except health and pairing. People (step 3, spec `docs/superpowers/specs/2026-10-18-webrtc-people-design.md`): `auth.json` holds people, and every device and pairing code belongs to one; owner status is the person's, and an admin action that would leave no owner device answers 409 `last-owner`. A code is plain (10 minutes) or an invite (3 days); people a code made who never paired are pruned, and spent or withdrawn codes are unregistered from the rendezvous. `bdj-store.ts` keeps each person's BD-J saved data (`/data/users/<personId>/bdj/`, one ustar file per scope, `persistent/<orgId>` or `buda/<orgId>/<discId>`, replaced atomically, etag from the file's identity with a strictly increasing mtime, 16 MB per scope and 256 MB per person); `routes/bdj-store.ts` serves it to the token's own person (spec §5 is the contract with BD-J 5e). `TITLE_LIBRARY` is the gate: `owners` answers every title route 404 to a guest, `everyone` (the deployed value) opens them; the owner can change it. The rendezvous Worker (`rendezvous/`, Cloudflare Worker with a Durable Object) maps a pairing code to the NAS and its address: the NAS registers its key and signed code hashes, the app looks a typed code up. `NAS_IDS` (a secret, comma-separated, beside `TURN_NAS_IDS`) locks a Worker to those NAS ids (403 `nas-not-allowed` at registration, and lookups, signalling and `/turn` refuse others); unset or empty it is open, which is what a self-hoster's own Worker wants. A pairing link is `<APP_URL>?pair=<code>` plus `nas=<server API base>` (no Worker: redeemed straight at the server) or `rv=<Worker URL>` (the server has `RENDEZVOUS_URL`), parsed by `src/ui/nas/pair-link.ts` (https only; `http:` loopback on a loopback-served app); the app asks before pairing with a server or Worker that isn't its own, a pairing keeps the Worker it was made through (`NasPairing.rendezvousUrl`, so WebRTC reconnects use it) and `direct` marks a `nas=` pairing with no Worker, and "Use another rendezvous" on the pair screen takes a Worker for typed codes. The client side is `src/ui/nas/`: `NasClient` (pairing, requests, local-network-access prompt and error messages), `NasStore` (pairings), the pair and preflight screens, the title screens (`TitleLibrary`, series, season, music) and the owner screens (admin, Unsorted, "file differently", Hidden), each with a pure model file; discs open through `RemoteSource` (`packages/engine/src/disc/`), a `ByteSource` that reads byte ranges from the module worker with read-ahead (`HttpTransport`, `nas-api.ts` for the shared types). WebRTC route (step 3, spec §6): when the NAS isn't reachable over HTTPS, the app reaches it through a data channel. The wire protocol is `packages/nas/src/rtc-wire.ts` (request and response frames, messages of at most 65536 bytes for Safari, caps of 64 requests and 16 MB queued), and `port-fetch.ts` serves the same `fetch` over a `MessagePort`, so the engine and the BD-J worker read through one `discFetch`. The NAS side is `server/src/rtc/`: `dispatch.ts` answers API requests from a channel and refuses them until a session is proven (the same token auth as HTTPS, never a proxy address as `remoteAddress`, forwarding headers stripped, read errors generic); `peer.ts` (werift 0.25.1, pinned) runs the peers; `udp-mux.ts` puts every peer on one UDP port (47998 by default, `RTC_PORT`, forwarded on the router) by routing on the ICE ufrag pair and moving a remote only after a STUN integrity check; `public-address.ts` finds the public IPv4 to advertise; `signalling-client.ts` keeps the socket to the Worker with a ping/pong heartbeat (exactly `{"t":"ping"}`, answered by the Durable Object's WebSocket auto-response so it never wakes the object) and backoff, and re-registers on a bad-auth close; `relay.ts` is the optional Cloudflare TURN relay's owner switch and monthly allowance, with usage counted from werift's per-pair counters as an estimate (the TURN credentials the Worker mints stay usable for an hour outside a session). The rendezvous Worker's `Signalling` Durable Object (`rendezvous/src/signalling.ts`) forwards offers, answers and candidates between the NAS and a device (per-IP and per-NAS limits, a 60 s device socket life), and `/turn` (`rendezvous/src/turn.ts`) mints TURN credentials only for the NAS ids on an allowlist, 30 an hour per NAS and 500 a day in all: set `TURN_KEY_ID`, `TURN_KEY_API_TOKEN` and `TURN_NAS_IDS` (comma-separated NAS ids) with `wrangler secret put`, never in the repo; without them it answers 503 `turn-not-configured`, and a NAS not on the list gets 403. The client is `src/ui/nas/rtc/` (`RtcConnection`, signalling client), `route-choice.ts` (HTTPS first, 2 s, then WebRTC) and `NasClient.discFetch` (a disc opened over WebRTC reconnects over WebRTC only); the relay UI is `RelaySettings.tsx` (owner switch, usage, a confirm before paid use), `RelayBadge.tsx` and `relay-model.ts`. Test flags are listed under the main thread. Buffer first (spec §7 of the step 3 spec): the pre-flight (`buffer-model.ts`) compares the probe with the rate of what plays (an episode's playlist, else the main title) plus 10% and plays at once, buffers silently (a wait under 120 s), asks (Wait, or Play now with pauses; a lower quality is picked from the pre-flight's level list instead), offers pauses when `navigator.storage.estimate()` (plus what the cache already holds) can't hold the lead plus two segments, or offers only pauses when the engine reported no cache (`readAheadCache` event at its start). Wait opens the disc with `bufferFirst`: the engine (`packages/engine/src/disc/cache-fill.ts`) fills the playlist from the EP map into `ReadAheadCache` (`disc/read-ahead-cache.ts`: OPFS through sync access handles, per disc, in 64 MB segment files named with each file's size; cleared when another disc opens, and after 24 h, also at the engine's start; `PlayerDeps.readAheadCacheRoot`) until it holds the target, then opens the disc and keeps filling ahead of the play position to the playlist's end (a seek restarts it there; it idles while another playlist plays), holding at most the target plus one segment ahead (lowered on a full disk) and freeing segments playback has passed; it keeps one request in flight while a playback read waits on the network, two otherwise. "Play now with pauses" opens at once with the same capped fill behind it. `RemoteSource` reads the cache, then the fill's in-flight chunk, before the network. A failed fill read is retried (1 s, 2 s, 4 s, then every 10 s, resuming at that chunk); `bufferProgress` reports the lead, and `stopped` when the fill failed for good (the disc changed, the device was unpaired, or two minutes of failures) or there is no cache (the player then says it will play with pauses); `bufferAhead`/`cancelBuffer` fill or stop it on an open disc. NAS screens and playback live in the address bar under `/nas/…`: `src/ui/nas/nas-route.ts` parses and builds the paths, `NasHistory` (`nas-history.ts`) is the one place that pushes, replaces and listens for popstate, `PlayingRoute` keeps a play link current while a NAS disc plays, and a play link names its disc by the key from `packages/nas/src/disc-key.ts`, which the app resolves with `GET /api/discs/resolve/<discKey>`; a link this device can't open shows the not-found screen (`NasNotFound`). Uploads (`server/src/encodes/uploads.ts`, `UploadStore`; owner devices over HTTPS only, 403 `https-only` on a data channel): `POST /api/encodes/uploads` `{ size, sha256, name }` answers `{ id }` (409 `in-progress` for another device's open upload of the same name; this device's own is answered again when size and hash match, so a lost answer is resumed, and dropped for the new one when they differ; 507 `no-room` under size plus 1 GiB free), `PUT uploads/<id>` takes `Content-Range: bytes a-b/size` (at most 16 MiB, any order, resendable; 413 or 400 refusals close the connection), `GET uploads/<id>` the stored ranges, `POST uploads/<id>/complete` checks every byte (409 `incomplete` with the missing ranges), the SHA-256 (422 `hash-mismatch`, upload removed) and the title and `EPISODE` tags (422 `bad-tags`, upload kept, for a file `titleFromTags` can't title), then renames the file over `<titlePart>/<episode>.mkv` and lists it, and `DELETE uploads/<id>` aborts. `DELETE /api/encodes/<id>` (owner) saves the index first, then deletes the file. Uploads live in `.uploads/<id>.partial` with `<id>.json`, and one untouched for 24 h is swept at start and hourly. Client: `src/ui/nas/fansub-model.ts` (pure), `FansubLine` (Find fansubs and the marks), `FansubEpisodePanel` (Line up again, Use original timing, offset), `FansubLanguages` (admin screen) and `src/ui/ToshoSearch.tsx` (the Subtitles menu's "Search Anime Tosho…"); the component tests use jsdom and `@testing-library` with `// @vitest-environment jsdom` at the top of the file.

Quality levels (step 4, spec `docs/superpowers/specs/2026-10-19-lower-quality-design.md`; phase 1, the NAS side): the NAS re-encodes a disc's video on the GPU and serves it as another version of the same disc, with the same paths, so the engine reads it like any NAS disc. `server/src/levels/`: `levels.ts` defines the levels (`h264-1080`, `phone-720`, `hevc-1080`, `hevc-1080-hdr`, `h264-1080-sdr`), which a disc is offered at (MPEG-2 and VC-1 never at `original`), and the byte plan, from the CLPI alone: EP intervals under 2 s are merged with the next (a clip's last with the one before; the merged-away entries leave the level's EP map), and each interval gets a fixed budget (the level's peak rate, at least an IDR; the kept audio at its rate in source packets; graphics at 1.5 Mb/s plus 50 kb/s per PG stream beyond the first and 1 Mb/s per IG stream, at least 32 KB per stream), so the rewritten EP map and the file sizes are known before anything is encoded; an interval that still overflows with its video at the floor drops whole PES of PG streams, highest stream numbers first, and of IG streams only once every PG stream is gone (`shedGraphics` in `remux.ts`; PG drops are logged once per clip, IG drops every time), then gets one try at 250 kbps; one that fits at no rate fails its reads with a 500, remembered in memory per plan so it isn't re-encoded every 5 s. `clpi-writer.ts` and `mpls-writer.ts` (with `sections.ts`) rewrite the CLPI (coding type, format, rate, EP map, kept streams) and the MPLS STN tables; `level-discs.ts` reads a folder or ISO disc's originals and `level-version.ts` builds a version (disc, level, audio stream) of the disc's video clips with its manifest; `audio-core.ts` keeps one audio stream (TrueHD and DTS-HD reduced to their cores) plus PG/IG and writes the PMT; `encoder.ts` runs ffmpeg per run of intervals (the run's bytes piped to it, keyframes forced at the EP entries' frames, each encoded frame given back its source frame's PTS and DTS by `SourceFrames`, since ffmpeg 7.1's QSV filters (Debian's build and Jellyfin's alike) round PTS down to their frame-rate grid, which `test-backends.ts` mimics for the tests; an over-budget interval re-encoded at a lower rate, never served oversized; a VC-1 source is decoded in software, because `vc1_qsv` dropped frames (measured with jellyfin-ffmpeg), and uploaded to the GPU for scaling and encoding, with ffmpeg at nice 10) and `remux.ts` interleaves the encoded video with the kept packets and pads to the budget; `clip-run.ts` (`ClipRunner`) drives one viewing's encoder up to 120 s of film ahead of its reads (a read within 10 s of film of the encoder waits for it, one further ahead restarts it there); `segment-cache.ts` keeps encoded intervals under `/data/transcode` (an LRU by bytes, `TRANSCODE_CACHE_BYTES`, 50 GB by default, keyed by the clip's size and mtime); `capacity.ts` leases GPU capacity per viewing (frames per second against `GPU_BUDGETS`, one lease per device and disc, gone after 2 min untouched); `backend-check.ts` picks the backend from `LEVELS_BACKEND` (`qsv` by default, `x264` for dev and CI, `off`) and self-tests each codec's encoder at start, offering only the codecs that pass; `level-service.ts` (`LevelService`) ties them together. Routes (`routes/discs.ts`): `GET discs/<id>/levels?hevc=&hevc10=&hdr=&audio=` lists the levels with their rates (priced with that audio stream, 1 by default) and why one is unavailable, `GET discs/<id>/manifest?level=&audio=` leases the GPU for the token's device, `GET discs/<id>/files/<path>?level=&audio=` reads at most 4 MiB and answers 503 `Retry-After: 1` while the encoder hasn't reached the bytes (503 `busy` with a message when the GPU has no room), and `DELETE discs/<id>/viewing?level=&audio=` releases the lease; without a working backend every level route is 404. ffmpeg is Debian 13's in the image (`FFMPEG_PATH`, `FFPROBE_PATH`; the iHD driver from `intel-media-va-driver-non-free` and `libmfx-gen1.2`); `server/deploy/deploy.sh` adds `compose.gpu.yaml` (the render node and its group) only when the NAS has `/dev/dri/renderD128`. Client side so far: `HttpTransport` takes the level's query and waits out a 503 by its `Retry-After` (exposed through CORS by `cors-policy.ts`), or by the body's `error: 'retry'` when the header can't be read (`busy` fails the read); phase 2, the UI, is in: the pre-flight asks `levels` and `GET discs/<id>/levels` (10 s, then Original only) and, when the NAS offers more than one level, lists them as radio rows (`level-list`, `level-option` with `data-level`, notes such as `plays now` and `about N minutes`, `level-busy`), preselecting the auto choice ("phone" there is the constrained memory profile or a small screen) and disabling Play until the answer arrives; `src/ui/video-caps.ts` probes what the browser can decode, so a level or Original it can't play is disabled; `LevelSession` (`src/ui/nas/level-session.ts`) holds the viewing lease and the switch; the Quality menu (`quality-menu`, `menuitemradio` items with `data-level`) sends `setLevel` to the engine, which reopens the disc at the level at the same place (`snapshot.levelSwitch`, `level-notice`), the `level-badge` shows `<label> · re-encoded on the NAS`, and the Audio menu at a level reopens the level with that audio. The E2E stand-in runs `LEVELS_BACKEND=x264` (CI installs ffmpeg for the `e2e` job too; HEVC levels answer `no-encoder`) with `LEVELS_GPU_SCALE=8` (the server multiplies its GPU budgets by it; only the stand-in sets it, because phone-sized screens lease a level and a lease lapses 2 minutes after its last read), and Playwright's desktop projects set a 1920x1080 `screen`, because the auto rule takes a screen under 600 px on its shorter side for a phone (a 1280x720 viewport is not one; the 1920x1080 screen is realism). A NAS test that needs Original picks it in the level list. `scripts/verify-level.ts` checks a level against a running server.

Places (resume, spec `docs/superpowers/specs/2026-10-20-permalinks-resume-design.md`): a place is one person's `PlaybackPlace` (`packages/nas/src/nas-api.ts`) per disc and playlist: the disc key (`d.` disc id or `f.` content fingerprint, so two copies of a disc share places), time, duration, `finished`, the program's registers (mode `hdmv`, `bdj` or `none`, PSR4's title, all 128 PSRs, the non-zero GPRs) and `PlaceSettings` (`audioLanguage`, `pgLanguage`, the `textFiles` added with their size, placement and offset (and, for a subtitle from the NAS, its `subtitleId` and `language`), PSR1-3, text on and scale, shader set, volume, mute), `updatedAt` and the device's name. A playlist makes a place when the user launched it (an episode or a link), it is the disc's main title, or it lasts 300 s or more (`PLACE_MIN_DURATION_US` in `src/ui/place-model.ts`, `?placemin=` in tests); a menu loop never does and leaves the last place as it was. `finished` (`isFinished`: ended, past the start of a last chapter that starts in the final 10%, or past 95% with no chapters) and the short place (`isShortPlace` in `packages/nas/src/place-rules.ts`, shared with the server: before min(30 s, 5% of the playlist)) decide what is offered: a finished place resumes nothing (Play starts over, and Up next moves on), and a short one asks nothing and stays off Continue watching. `src/ui/nas/resume-model.ts` (`resumeOffer`: none, short, ask, changed) turns a disc's places into the pre-flight's offer, and `changed` (the playlist is gone or a different length) offers only Start from beginning. The engine side is in `protocol.ts`: `open` takes `start: StartPoint` (playlist, time, and for HDMV a title with its saved PSRs and GPRs, else PSR1-3), so a disc opens at a place instead of First Play; `readPlace` is answered at once with `placeState` (the registers, in command order) for the saver; `startFailed` says a start playlist is not on the disc (nothing plays) or its time is past the end (it plays from the beginning). `RegisterFile.snapshot`/`load` (`hdmv/registers.ts`) carry the registers, and `Navigator.resumeTitle` resumes an HDMV title at its playlist and time with them (an approximation, see `docs/known-issues.md`); a BD-J disc is resumed directly at the playlist with BD-J off (Menu boots it fresh). A play link (`/play/<discKey>?pl=&t=`, `resume=1` to resume) now starts in the engine through the same `open { start }`, never racing First Play; `play-once-open.ts` is gone, and `src/ui/nas/missing-start-notice.ts` says an episode isn't on its disc and opens the top menu. `src/ui/place-saver.ts` (`PlaceSaver`) saves the open disc's place every 10 s while playing and at once on a pause, seek, track, offset or shader change, on close and on the page hiding; it writes the device first (`PlaceStore`, `src/ui/place-store.ts`, IndexedDB version 6: `places`, `placeOutbox` and the subtitle files added per disc, 5 MB each and 50 MB a disc). A local folder's or disc-server disc's place goes into `places` and stays on the device. A NAS disc's place never goes into `places` (a local copy shares its `f.` key and would offer another person's place; version 6 drops those version 5 stored, told apart by their NAS disc id): its device-first write is the outbox, scoped to the pairing it was saved under (a place never goes to another NAS or person), sent from there with a `keepalive` request when the page is going away (HTTPS only, bodies up to 60,000 bytes) and a 15 s timeout (`NasClient.putPlace`), and straight to the NAS when the outbox can't be written. A network error, a plain 404 (a NAS without the place routes), 429 and 502–504 wait; 400, 413 and 404 `bad-key` drop the place at once; any other error answer counts toward five attempts, then drops it; `stale` means the NAS has a newer one. A playlist left within 1 s of its end (a disc program moves on before the player says ended) is saved finished. `src/ui/place-apply.ts` applies a place's settings once the disc has opened (audio and PG by index or, for Up next, by language; text files re-added from the device (a stored subtitle is fetched again from the NAS, see the subtitle store); volume; never the shader set, which stays this device's own choice, Off on a new device) and never overrides a pick the user made since. The NAS keeps them in `server/src/playback-store.ts` (`PlaybackStore`, `/data/users/<personId>/playback/<discKey>.json`, replaced atomically under a lock, at most 500 places a person, an `updatedAt` more than five minutes ahead of the server's clock clamped to it, an older place answered 409 `stale`, bodies up to 256 KiB); `routes/playback.ts` serves `GET`/`DELETE /api/me/playback/<discKey>`, `PUT`/`DELETE` of a place by playlist id, the Continue watching list and per-title progress to the token's own person, and a malformed key answers 404 `bad-key`. `packages/titles/src/up-next.ts` is pure: it builds Continue watching (a resume card for every unfinished place that isn't short, and an Up next card for the episode after a series' newest finished one) and per-episode progress from the places and the live catalogue, and when `TITLE_LIBRARY` is `owners` a guest gets the plain resume cards without catalogue names. The UI: `ResumePrompt` (Resume at m:ss, Start from beginning) in the pre-flight (`Preflight.tsx`), `ContinueRow` over the title library, progress marks and a resume link on episodes in `SeasonScreen`, and for a local folder `src/ui/local-resume.ts` (`askOrOpen`, `recentResumeLabel`) asks before opening and puts "Resume at m:ss" on a Recent discs row.

Subtitle store (piece 3 of the same spec): `server/src/subtitle-store.ts` (`SubtitleStore`) keeps owner-uploaded subtitles under `/data/subtitles/<id>/` (`meta.json`, the file in `sub/`, fonts in `fonts/`, written atomically under a lock). A subtitle file is an `.srt`, `.ass` or `.ssa` of at most 5 MB, fonts (`.ttf`, `.otf`, `.ttc`, `.woff`, `.woff2`) at most 50 MB per upload, and the store 2 GB in all; a name must be a plain name of at most 255 bytes with an allowed extension. Errors are `TooLargeError`, `BadNameError`, `EmptyBodyError` (a subtitle file with no bytes) and `NotFoundError`; an upload that was created but never got its file is removed after 1 h, and the font sum is checked again at commit, so two parallel font uploads can't pass the limit together. `server/src/routes/subtitles.ts` serves them behind the device token: only an owner device creates (`POST /api/subtitles`, with an attachment), uploads (`PUT` of the file and of each font by name), edits (`PATCH`: name, language, default offset, attachment) and deletes, and anyone else's write answers 403; reads (the list by `discKey` or `titleId`, a subtitle's file and fonts) are open to every paired person, and `?all=1` lists every upload to owners only (403 otherwise; NAS settings' **Subtitle uploads**, `SubtitleUploadsSection.tsx`), under the `TITLE_LIBRARY` gate like the title routes; the file and font downloads are behind the gate too, stricter than spec §7.1 asks, on purpose (a guest behind a closed gate can't list them either). An attachment is an episode (title, season, episode number, resolved through the catalogue to a disc key and playlist) or a chapter of a disc's playlist (disc key, playlist, chapter, and the title it was uploaded from); the route sets `attached` on every subtitle, false when its disc or playlist no longer resolves, and only owners are shown those (a non-owner's list also leaves out `uploaderPersonId`). The `titleId` listing includes chapter uploads by their stored `titleId` and by the disc keys of the title's discs, and episode uploads by those disc keys once the title id they name is gone (a rematch). A refused `PUT` (too large, empty, bad name) answers with `Connection: close` so the unread body doesn't hold the socket, and the effective font limit (what is left of the 50 MB) is checked before the body is read. `bodyStream` and `readBody` (bounded body reads) now live in `server/src/http.ts`, shared with the BD-J store. The client is `NasClient`'s subtitle methods (`subtitlesForDisc`, `subtitlesForTitle`, `subtitleFiles`, `createSubtitle`, `uploadSubtitleFile`, `uploadSubtitleFont`, `updateSubtitle`, `deleteSubtitle`; names are percent-encoded, and a refused upload aborts its request) and `src/ui/nas/subtitle-model.ts` (pure: the upload checks and limits, languages, offsets, which subtitles belong to a playlist or season, `uploadSubtitle`, error messages, the targets an owner can attach to). Owners get `SubtitleUpload` and `SubtitleList` (`src/ui/nas/`) on the season and movie screens: upload, Edit and Delete, and a "Not attached" group on each of a title's screens for uploads whose disc or playlist is gone, and for episode uploads whose season is no longer one of the title's (`ownerListing`; the NAS still calls those attached and viewers get them; see `docs/known-issues.md`), where Edit stays disabled until the discs' keys have loaded. Upload progress is reported as the bytes go: over HTTPS through XMLHttpRequest's upload events (Safari can't stream a fetch body), over WebRTC by counting what the channel reads (`src/ui/nas/upload-progress.ts`, `NasClientDeps.sendWithProgress`). In the player the Subtitles menu has a "From the NAS" group for the open NAS disc's playlist; `StoredSubtitlePicker` (`src/ui/nas/stored-subtitle-pick.ts`) fetches the file and fonts and adds them to the text set as a user pick (the newest pick wins through a generation counter, a local pick calls `supersede()`, it waits out the encoding prompt, and a failed fetch or a timed-out wait shows a notice; a cancelled encoding prompt, counted by `PlayerController.encodingCancels`, ends the wait without one), using `pickedSubtitles()` in `packages/engine/src/controller/drop-files.ts` to choose the files as a local pick does. Stored subtitles live in places: `PlaceTextFile.subtitleId` and `language` are written by `PlaceSaver.noteStoredSubtitle`, and on a resume `place-apply.ts` fetches each stored subtitle again from the NAS (bounded to 15 s, `STORED_FETCH_TIMEOUT_MS`; the download is aborted at the timeout or a newer pick) and a newer user pick gives way over it through `LaunchSettingsApplier.supersede()`, which Up next's carry checks too; Up next carries a stored subtitle to the next episode only when text was on, picking that playlist's stored subtitle in the same language (at its default offset), else PG by language.

Testability pattern: `Player` takes its side effects through `PlayerDeps`: `emit`, `videoCodecApi`, `nowMs`, `requestFrame` and `createCompositor`. `PlayerController` takes a `WorkerLike` and an `AudioOutputLike`. Unit tests inject fakes, for example a fake `VideoDecoder` that can deliver output late. Keep new browser APIs behind injectable interfaces like these.
